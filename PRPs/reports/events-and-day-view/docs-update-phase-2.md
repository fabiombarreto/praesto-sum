## Candidate Decisions (for operator review)

The following were observed in the patch or the PRD but are inferred or not stated as a decision, so they were NOT written to `docs/decisions.md`, `docs/anti-patterns.md` or `docs/context/conventions.md` per the PRESERVE-ENTIRELY rule. Review and add manually if stable:

- **`formatVersion` stays 1 when only keys are added.** The `src/shared/export.ts` header says "unit 14 only ADDED the `events` and `event_sync_links` keys, which no reader of the earlier shape trips on", and `docs/api-reference.md` repeats it. No ADR or `documentation/` file states the versioning rule (a grep of `documentation/` for `formatVersion` finds nothing), so the rule currently lives only in a code comment. Candidate decision: additive keys keep `formatVersion` 1; a removed or retyped key bumps it. The restore drill's key-order dependence (a link references its Event, so `events` precedes `event_sync_links`) is the companion fact.
- **The two-character search floor is server-side on `/api/events` and client-side on `/api/tasks`.** `GET /api/events` answers 400 naming `q` for a `q` under `SEARCH_MIN_QUERY_LENGTH` (2) after trimming; `GET /api/tasks` has no such server floor (its `validateSearchQuery` only rejects blank and over-length). PRD AC-17 says a one-character `q` is 400 "exactly as on `GET /api/tasks`", which the shipped Task route does not do; the hybrid code review recorded this as a PRD wording discrepancy, not a failure. `docs/api-reference.md` documents the Events behaviour correctly. Candidate: reword AC-17 in the PRD (operator-owned) or accept the asymmetry as intentional; do not change `GET /api/tasks` (it is a frozen contract, AC-18).
- **The `q`-only sort reads the ambient clock for the owner's UTC offset.** `src/worker/routes/events.ts` orders an unbounded search by `coalesce(start_at, local midnight of start_date)` using `offsetMinutesAt(new Date(), PRAESTO_TIMEZONE)`. The route comment states this is exact for `America/Sao_Paulo` since 2019 (a fixed -03:00); it would misplace an all-day Event by an hour in a DST zone. Candidate constraint for `docs/context/constraints.md`: the owner's zone has no DST; revisit if it changes. The review flagged the clock read as advisory.
- **A closed-key allowlist that also applies to `POST`.** `POST /api/events` refuses any key outside `EDITABLE_EVENT_FIELDS` with a 400 naming it (the Life Areas `PATCH` does the same), which is what keeps a caller from choosing `source` or forging `contentHash`. Candidate convention for `docs/context/conventions.md`: for entities with server-owned fields, the allowlist applies to create as well as edit.
- **`PATCH` semantics that are easy to misread.** When only `startAt` or `startDate` moves, the end is NOT moved with it (the caller sends both); `title`, `allDay` and `timezone` cannot be `null`; setting `allDay` carries only the target shape's fields. All three are documented in `docs/api-reference.md` as facts. Whether "send both" is the permanent contract or the sheet (phase 4) should shift the end for the owner is a phase 4 decision, not recorded here.
- **Carried over from the phase-1 manifest, still open:** the four-character non-blank CHECK idiom, the two coexisting wall-clock-to-instant functions with different DST-gap semantics, the `EventRow`/`NewEventRow` naming, and the Web API globals inside `src/shared/`. Phase 2 adds no new instance (`event-range.ts` imports only `events.ts` and uses no global).
