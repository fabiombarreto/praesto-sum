# UI/UX guidelines — research evidence (A1, 2026-08-18/19)

Raw, fact-checked research that `documentation/40-engineering/ui-ux-guidelines.md` was written from. Three workflow passes: (1) adversarial verification of the 21 PWA-practice claims from the plan's scouting; (2) gap research — Android/Windows standalone specifics, pt-BR copy + WCAG 2.2 Level A, guideline-document craft + performance-budget tooling; (3) adversarial verification of (2). Verdicts are `confirmed` / `corrected` / `unverifiable`; every finding carries its source URL. Numbers in the guidelines follow the *corrected* values here. Kept verbatim as an evidence record — not maintained.

 Research for the UI/UX guidelines document on the Android-Chrome + Windows installed-PWA specifics (items 1–11), done 2026-08-18/19 against developer.chrome.com, web.dev, MDN, Android developer docs, Microsoft Edge docs, Chromium source and blink-dev. Headline conclusions: (1) on Android back is a first-class close signal — Chrome ≥126 maps the back gesture to CloseWatcher/<dialog>/popover automatically, so use native <dialog>/popover or CloseWatcher for sheets rather than hand-rolled pushState; at history root back leaves the app (Android 12+ backgrounds the task); predictive-back previews for web content do not yet exist in Chrome (Chrome 138 only added a dimmed back-swipe preview in tabs; PWA coverage unverified). (3) window-controls-overlay (Chromium/Edge 105, desktop only) gives ~30 px of title-bar area and a custom drag region but costs: user can toggle it off, must code env(titlebar-area-*) fallbacks and app-region drag/no-drag, loses overlay on cross-origin navigation, spoofing/fingerprinting concerns, no mobile effect — a "nice-to-have later" for a single-user Tasks app. (4) Native date/time pickers are system dialogs you cannot style (only color-scheme darkens them), showPicker() needs a user gesture; enterkeyhint/inputmode are Baseline; autofocus shows the keyboard on touch (MDN) but is an a11y/scroll hazard — fine only for a deliberate quick-capture screen; the 16 px anti-zoom rule is iOS-specific, on Android the real issue is never disabling zoom (WCAG 1.4.4) and, since Chrome 108, the keyboard no longer resizes the layout viewport (use interactive-widget=resizes-content for a bottom capture bar); Chrome 135+ edge-to-edge needs viewport-fit=cover + env(safe-area-inset-bottom) (PWAs still not edge-to-edge as of July 2026, fix in progress). (5) Use :focus-visible (Chrome 86, Baseline 2022), never outline:none without replacement, ≥3:1 contrast, ≥2 px, and the Chrome-83 style dual ring (dark+white) to survive both backgrounds. (6) navigator.vibrate works on Chrome Android only after a user tap (sticky activation, Chrome 60), max 10 000 ms / 999 entries, silently no-ops under silent/DND; no Safari/Firefox. (7) Notifications: Android truncates title to one line (~30 chars recommended), body ~40 chars collapsed; badge 72 px monochrome (Android-only), icon ≥192 px, image ≥1350 px wide, actions limited by Notification.maxActions (icons 128 px for Android, Android 7+ hides action icons), tag replaces silently, renotify needs tag, silent beats renotify, requireInteraction matters on desktop only (Android persists anyway), vibrate option deprecated Android 8+; Android 13 POST_NOTIFICATIONS is off by default and the exact WebAPK prompt path is unverified — request from an in-app gesture and test. (8) content-visibility:auto + contain-intrinsic-size:auto (Chrome 85; 232→30 ms in web.dev demo) is the first lever, windowing (react-window, ~1000-row demo, overscan 1) for thousands of rows; history.scrollRestoration='manual' + Navigation API scroll:'manual' for SPA scroll restore.
