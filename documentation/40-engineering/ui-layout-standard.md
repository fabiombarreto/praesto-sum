# UI Layout Standard

> **Purpose:** The skeleton every Praesto screen shares — navigation model, screen anatomy, the anchor screens, state placements and desktop adaptation — so units build *on* a standard instead of inventing one per screen.
> **Update when:** A new screen does not fit the anatomy (fix the standard or record the exception here), a third destination of equal daily weight appears (the navigation rule flips), or a platform behaviour a rule relies on changes. Record each change in this document's [History](#history) — the [UI/UX plan](../50-planning/ui-ux-plan.md) that used to hold those rows closed `deprecated` on 2026-08-23.

Derived from UI/UX-plan activity A3 (research evidence: `PRPs/reports/layout-standard/01-research-evidence.md`; sketches: `PRPs/reports/layout-standard/sketches.html`). It implements the [guidelines](ui-ux-guidelines.md) (§2, §3, §8, §12) and the [identity](../10-product/visual-identity.md) (ADR-0010); values come from `src/app/tokens.css`. Active since 2026-08-20, when the owner chose the navigation model from the sketches.

## 1. Navigation model

**Decided (owner, 2026-08-20, from the sketches): model B — single screen + sheets.** Recorded here with the rejected alternative so the choice is not re-litigated:

- **(B) single screen + sheets — chosen.** *Hoje* is the only destination; *Pesquisar* (unit 8) and *Configurações* are icon buttons in the header; detail and filters open as native `<dialog>` sheets; there is no bottom bar. Evidence: Material 3 says not to use a navigation bar for fewer than three destinations and that settings are not a top-level destination; the single-user apps the owner admires (Things, Reminders, Google Tasks, Microsoft To Do) run without a bar; a bar would stack ~64 px of chrome under the 56 px capture field. Cost: whatever is not on *Hoje* is one tap behind an icon.
- **(A) bottom bar of three** (*Hoje · Pesquisar · Configurações*) above the deck — rejected for now: two bottom planes competing in the thumb zone, unequal destinations today, and the bar would have to hide while the capture field has focus.

**Flip rule (binding either way):** the moment Praesto has **three destinations of equal daily weight** (plausibly *Hoje · Agenda · Áreas* after units 4 and 13), the bottom bar enters on compact widths and the rail from 600 dp — never before, and never padded with unequal items. Tabs are not a bridge: *Hoje*'s groups are sections of one list, not peers.

## 2. Screen anatomy — phone (compact, < 600 dp)

Top to bottom, every screen that lists Tasks:

1. **Header (flat, never elevated):** page title as the `<h1>` (*Hoje*), the date in mono beside it (`qua., 20/08`; *amended 2026-10-19, unit 14: the date is a button that opens the Day route of item 11, with the same text, face and baseline, a 48 px hit area that grows upward only and no horizontal padding*), a remaining count as text (*4 restantes* — never a ratio or a progress bar: progress shown before the effort increases drop-off; the honest mirror lives in the group counts), and on the right up to three 48 px icon buttons: filters (with a numeric badge when any filter is active), then — in model B — search and settings. No wordmark in the header (it lives on the splash, the settings screen and the desktop rail).
2. **Offline / unreachable banner** (when applicable): directly under the header, one line, icon + action language, persistent while the condition holds, not dismissible (§8).
3. **Quick-filter chip row:** one horizontally scrolling row of 3–5 toggles (*Abertas*, *Para hoje*, *Alta prioridade* — **amended 2026-08-24:** the row previously offered *Com hora*; a Task carries no time of day, since `deadline` and `scheduledDate` are calendar days enforced by `tasks_single_date_chk`, so that chip named a filter the domain cannot express. It returns as an option only when Event ships in unit 14). The row holds toggles and nothing else — **amended 2026-08-24:** it previously ended with a trailing *Filtros…* chip, cut by the owner because the header's filter button (§2.1) already opens the same sheet and already carries the active-count badge; two doors to one room is the element that does not pay rent (guidelines §1, principle 4). Applied filters stay visible as selected chips; chips are 48 px hit areas with 8 px gaps. *(Amended 2026-10-12, unit 13 phase 4, pending the owner's confirmation: this sentence also promised a *Limpar filtros* chip. The Life Area filter is the first applied chip, and it is itself a toggle: while an area is picked it leads the row — never trails it, because at 375 px three quick chips already fill the row and a trailing chip would sit past the edge — and tapping it clears only the area (focus then moves to the first quick chip, so a keyboard user keeps his place in the row). Its visible label is capped at 10 rem with an ellipsis, because an area name may run to 40 characters and, uncapped, fills the row and pushes the three quick chips past the edge at 375 px (measured in the live pass, 2026-10-12); the full name stays as the chip's text and whole in the filter sheet. *Limpar filtros* lives in the filter sheet and in the filtered-empty state of §2.7, because a chip for it would be a non-toggle among toggles again, which the 2026-08-24 amendment above removed. Whether the owner wants that chip back is open; it is one element.)* Default state: nothing selected; a narrowing filter never survives a cold start silently. *(Amended 2026-10-21, unit 14 phase 5, PRD D-Q: *Com hora* stays withdrawn. Event has shipped, but a Task still carries no time of day and the owner's commitments live in the Agenda (item 4) and on the Day route (item 11), so a Task filter on time would still name a filter the domain cannot express. The sentence "It returns as an option only when Event ships in unit 14" above stays as history, now qualified: shipping Event did not make the chip expressible.)*
3.5. **Adherence line (unit 11 — added 2026-10-04, numbered 3.5 so no existing item moves):** one plain-text line directly below the chip row, inside the chip row's own grid cell. It is present only when an `active` Recurrence Series has at least two misses in the 30-day window, names the top series and its miss count plus "+N" for the other qualifying series, and opens `/settings/adherence` on tap (a 48 px target, muted text, no icon, no relief). Otherwise it is absent — no placeholder, no empty element, no reserved space — and a failed fetch is also absence, never a banner or a toast. It is never a ratio or a progress bar (§2.1 unchanged); an `ended` series never appears on it.
4. **Agenda stack (unit 4 hook):** today's Google events as **one** group at the top of the list, collapsed to the next event + count (*Agenda · 2*), expanding to rows with **no checkbox**, a leading time column, a calendar glyph and a dashed outline treatment — never interleaved with Tasks, never in the accent colour; tap opens Google Calendar (read-only). *(Amended 2026-10-19, unit 14 phase 3: the stack now also lists the owner's own commitments beside Google's, as rows with a solid outline on a filled ground, a different calendar glyph and no checkbox; Google's rows keep their dashed read-only look and their link. The group is one and **Agenda · N** counts both kinds, all-day rows first and then by start. The collapsed state shows the name and the count only, as it has since unit 4: the "collapsed to the next event" wording above was never built and is recorded here as such, not silently deleted. The Agenda never reads as a free day while a source has not answered: a Google outage or partial answer shows the explicit notice of unit 4, a failed commitments request shows a status line of its own with the generic request-failure sentence, and while either source is still loading the empty text is withheld, as `decideAgendaNotice` decides. Amended 2026-10-21, unit 14 phase 4: phase 3 shipped the commitment row with no control at all, so that nothing invited a tap that did nothing; a local row is now one `<button>` that opens the Compromisso sheet on tap (§3), on *Hoje*'s Agenda as on the Day route and in search, while Google's rows are unchanged and stay read-only links to Google.)*
5. **Groups, in this order,** each with a 40 px header carrying name + count (counts stay visible when collapsed — the "my tasks vanished" trap): **Atrasadas** first (collapsible; header action *Reagendar para hoje*; rows also show the overdue date inline in the live/overdue colour, so lateness is visible away from the header) → **Hoje** (never collapsible; sorted by time, then priority) → **Próximas** (collapsed by default) → **Sem data** (collapsed by default — no major app shows undated items on Today; here it is a deliberate "pick something" drawer) → **Concluídas** (`done` Tasks only) → **Não concluídas** (`missed` occurrences — the permanent record the cron sweep writes; collapsed by default, count visible when collapsed). Both closed groups are collapsible. Collapse state persists per group on *Hoje*; search renders the same two groups and keeps *Não concluídas* collapsed by default without persisting it.
6. **Row anatomy:** 64 px minimum (the project constant), leading 48 px completion control (every task app leads with it), title on **two lines then ellipsis** (`line-clamp-2` — amended 2026-08-23 to match [guidelines §12.4](ui-ux-guidelines.md), which sits above this document and which A5 implemented; Portuguese titles run ~15 % longer than English and one line truncated too many of them), a second metadata line in mono (*até 18:00* · *venceu seg., 18/08* in the overdue colour · priority glyph + word · the area name as text, last on the line — never a dot or a colour), at most **one** trailing element, never a chevron. Tapping the row opens the detail; swipe actions, if ever added, are shortcuts to visible controls (guidelines §12.4), never the only way.
7. **Empty state:** inside the list region, centred between header and deck: *Nada para hoje.* + one cue (*Bora capturar a primeira?*) + **one CTA that focuses the capture field** (*Nova tarefa*). *Amended 2026-08-23:* this rule originally said "no duplicate button", written before the microcopy the owner approved and before [guidelines §8](ui-ux-guidelines.md) settled on "one CTA that focuses capture"; A5 shipped the CTA and it is the rule now. The button is not a duplicate of the deck — it moves focus to it, which is what an empty state is for. Filter-induced empties read *Nenhuma tarefa com esse filtro.* + *Limpar filtros*. Per-group empties collapse to one line or are omitted.
8. **Toast:** above the deck, one at a time (§8); while a sheet is open the *same* toast element is rendered **inside the dialog's subtree**, through a slot the sheet exposes — otherwise it is inert under `showModal()`. *Amended 2026-08-23:* the rule used to prescribe `popover="manual"` for that case. A5 found the simpler answer: a manual popover in the top layer is itself inert under a later `showModal()` unless it lives inside the dialog, so the popover buys nothing here and adds a second top-layer element to reason about.
9. **Capture deck:** bottom-anchored, the one elevated plane; eyebrow *Nova tarefa* in mono, 56 px field with the icon-only 48 px submit (*Adicionar*); `autofocus` here and only here when the app opens on *Hoje* (guidelines §12.5); disabled with an inline hint while offline.
10. **No bottom bar** (model B). If the flip rule of §1 ever fires, the bar sits below the deck and hides (`translate` + `inert`) while the capture field has focus.
11. **Day route (unit 14 — added 2026-10-19, numbered 11 so no existing item moves):** `/day/AAAA-MM-DD`, reached from the *Hoje* header date (item 1) or by address, shows one date. It is a route with real history entries — every step to another date pushes one, and *Voltar* and Android back pop them — and not a destination of equal weight, so §1's flip rule is unchanged. Anatomy, top to bottom: a header with *Voltar* and the date as the `<h1>` (the pt-BR long date, with the year only when it is not the current one); a stepper row with *Dia anterior* and *Próximo dia* as 48 px icon buttons at its two ends and *Hoje* between them only when another date is shown; the offline banner slot of item 2; then, as the first element of the body, *Novo compromisso* (added by phase 4, recorded 2026-10-21) — the route's one primary action, disabled offline, which opens the Compromisso sheet of §3 prefilled with the date shown; then up to three sections in DOM order — all-day items, timed commitments with their start and end (`09:30–10:30`, and `até 01:00` on the day an overnight commitment runs into), and the open Tasks dated that day as rows without a time. The owner's commitments (solid outline) and Google's (dashed, read-only) are listed together; a Task row opens the Task through the same deep link a notification uses. A day with nothing reads *Nada neste dia.*, and only once Google, the commitments and the Tasks have all answered: a Google outage or a failed request shows its own line and never a free day. The data comes from the one pure range function (`itemsInRange`) that *Hoje*'s Agenda also calls.

## 3. Surfaces: detail, filters, dialogs

- **Detail and filters are native `<dialog>` sheets** (`showModal()`): bottom-docked on compact (rounded top corners, a 32 × 4 px handle, `max-height: 90dvh`, internal scroll with `overscroll-behavior: contain`), centred at max 560 px from **640 px** — *amended 2026-08-23*: A5 used Tailwind's existing `sm` breakpoint rather than adding a second one 40 px away, and measured the result (a centred 560 × 720 card at 1280 px). Mirror both the `close` **and** the `cancel` events into state: a close request can close the dialog without firing `close`, which strands the component's `open` flag. Android back and `Esc` close them (Chrome ≥ 126 close requests); focus returns to the opener natively; `html:has(dialog[open]) { overflow: hidden }` locks the page. **Never stack sheets.** Light dismiss (`closedby="any"`) only on the filter sheet — never on an editor with unsaved changes; the detail keeps its draft in memory on close (§8).
- **Detail content order:** title (editable), date as three chips (*Sem data · Concluir até · Fazer em*) + date input under its own visible *Dia* label, priority chips (*Alta · Normal · Baixa*), description, then *Cancelar* / *Salvar*; *Excluir* is a secondary button that opens the irreversible confirmation (§8). *(Amended 2026-09-30: once the owner picks a repetition in *Repetir*, *Sem data* is withdrawn from the date chips — a repeating Task needs a date, and offering the chip only to refuse the save was a trap. The mode is not switched for him; he picks *Concluir até* or *Fazer em*. A series occurrence keeps all three.)* Long flows (settings, diagnostics, export) are **routes** with real history entries, not sheets.
- **Compromisso sheet (unit 14 phase 4 — recorded 2026-10-21):** the sheet that creates, changes and deletes the owner's own commitment, a native `<dialog>` through the same sheet primitive as the Task sheet. *Novo compromisso* (§2 item 11) opens it empty and prefilled with the day shown; tapping a local row on the Day route, in *Hoje*'s Agenda or in search opens it filled; Google's rows never open it. Field order: *Título*, *Dia inteiro* (a chip), *Início* and *Fim* (each a *Dia* and, unless the commitment is all-day, a *Hora*, side by side), the resolved-end line right after *Fim* (*Termina em …*, announced as a status), *Fuso horário* (a native `<select>`, the owner's zone first), *Local*, *Descrição*, then *Cancelar* / *Salvar*. For an existing commitment only, a distant *Excluir* swaps the sheet's content for the irreversible confirmation *Excluir este compromisso?* with *Cancelar* focused (§8). The offline banner shows inside the sheet, above both the form and the confirmation, because `showModal()` makes the page behind inert. One draft is kept in memory per commitment and, for a new one, per day. There is no light dismiss (it is an editor with unsaved changes) and no success toast — the sheet closing and the list changing are the confirmation — and a failure stays in the sheet as a persistent line, never a toast.
- **Notification priming** (unit 7): a `<dialog>` sheet at the moment the first Reminder is saved or push is toggled in settings — never on launch; the real prompt fires inside the tap handler.

## 4. Keyboard (Android) — decided

`<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover, interactive-widget=resizes-content">`. The layout viewport shrinks like Android's `adjustResize`, so the deck rides above the keyboard with no script (Chrome 108+; the startup-height bug is fixed in Chrome 139). Required hygiene: the shell is a `100dvh` grid (header / scrolling list / deck) with `overflow: clip`; the list is its own scroll container; no height-based media queries; drop `safe-area-inset-bottom` from the deck while a field has focus, because the inset does not update under the keyboard — anchored on the **shell element** (`[data-shell]:has(input:focus-visible, textarea:focus-visible)`), *amended 2026-08-23*: MDN advises against anchoring `:has()` on `:root`, since every DOM mutation then re-evaluates it. Accepted trade-off: the relayout snaps rather than slides. Rejected: `VisualViewport` repositioning (script on every event, glitchy during the keyboard animation) and the VirtualKeyboard API (Chromium-only, documented geometry bugs in 2026). This resolves guidelines §2.6.

## 5. Desktop and Windows

- **≥ 640 px (tablet, desktop, a half-snapped window):** one pane — the list column capped at 640 px and centred; detail and filters open as the centred ≤ 560 px dialog of §3; the deck stays bottom-anchored inside the column; search and settings stay as header icons (no rail until the flip rule fires). *(Amended 2026-09-30: this section described a 600–839 dp side sheet and an ≥ 840 dp list + detail, neither of which was ever built — §3 had already moved the sheet to a centred dialog from 640 px on 2026-08-23, so the document contradicted itself. The ≥ 840 two-pane layout was **rejected** at Backlog triage the same day: four weeks of daily use on the PC produced no sign that the single column is cramped. **Reopen trigger:** the owner says the PC feels cramped. The rejected specification, kept for whoever reopens it: a fixed 420 px list pane with the same header, chip row, agenda, groups and deck; a flat detail pane with an empty placeholder; `Esc` clears the selection; shrinking below 840 keeps the detail and hides the list.)*
- **Keyboard:** everything works with Tab / Enter / Space / Esc (WCAG 2.1.1). Three accelerators exist: `/` opens search from *Hoje* — ignored while a text field has focus, and it never types itself into the search field; `Esc` closes the open sheet or the search, notifications and diagnostics screens (*amended 2026-10-19, unit 14: and leaves the day route of §2 item 11*; *amended 2026-10-21, unit 14 phase 4: `Esc` closes the Compromisso sheet of §3 and does not also leave `/day` or search — a second `Esc` leaves — and `/` is also ignored while a `<select>` has focus*); `Enter` saves an inline title edit and `Esc` cancels it. None overrides an OS shortcut. Windows below 640 px are treated as compact. *(Amended 2026-09-30: this bullet specified roving focus over the rows (`↑/↓` or `J/K` move, `Home/End` jump, `Enter` opens), `E` completes, `T` opens the date, `1–3` set priority, `N` focuses capture, shortcuts shown in tooltips and a help sheet — none of it was ever built, and none of it was ever triaged. **Rejected** by the owner at the rule-6(b) review, with the two-pane desktop it was written for. **Reopen trigger:** the owner misses keyboard shortcuts on the PC. Whoever reopens it: single-key accelerators need an off switch or a focused field (WCAG 2.1.4), as `/` already does.)*
- Window Controls Overlay is optional polish, deferred until the layout is stable.
