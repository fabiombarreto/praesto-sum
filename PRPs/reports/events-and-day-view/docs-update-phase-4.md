## Candidate Decisions (for operator review)

Review and add manually if stable:

- **A zone change alone moves a timed commitment's instants (plan decision D4-4).** The draft is wall-clock parts, so "09:00 in New York" replaces "09:00 in São Paulo" when only the zone changes (observed in the live pass, item 8: `{"timezone":"America/New_York","startAt":…,"endAt":…}`), the way Google Calendar treats a zone change; conversely, an untouched wall clock never produces a time key, so a title edit cannot move an Event stored in an hour that occurs twice. Stated in code headers and the plan, in no ADR. Candidate: a line in ADR-0016's follow-up or `docs/domain/areas/events.md` (the new section states the first half already). Reopen trigger recorded in the plan: the owner finds it surprising at the device proof.
- **Editing a start does not move the end (D4-8).** The patch then sends both `startAt` and `endAt`, and the inline reason names an end that falls before the start; Google Calendar preserves the duration. Reopen trigger: the owner reports "moving it an hour" needs two edits. Related to live-pass finding F1 (see the fourth Deferred Question). Candidate for a PRD Decisions Log row (owner-owned).
- **The zone select lists the runtime's whole IANA set, the owner's zone first (D4-3).** `Intl.supportedValuesOf("timeZone")` gives 418 options in the pane's Chromium; V8 omits `UTC` and `Etc/*`, so `timeZoneChoices` adds a commitment's own zone when the runtime accepts it; where the API is missing the list is the owner's zone and the commitment's. Candidate: a note under constraints that the zone list is the runtime's, not a curated set. Reopen trigger: the device finds the select unwieldy (the short list with search is the recorded fallback).
- **An unanswered or failed source must never read as "nothing found" — now two instances.** Phase 3 recorded it for the Agenda and `/day` (`decideAgendaNotice`); phase 4 repeats it for search (`decideSearchBody` says "nothing found" only once the Tasks AND the commitments have both answered and both are empty, and a failed commitments request never turns a Task result into an error). With two independent pure functions enforcing the same rule, the case for an entry in `docs/anti-patterns.md` ("Letting a failed or unanswered source read as an empty result") is stronger than at phase 3, but it still rests on code headers and the PRD's success metric, and that file's header says nothing there is inferred, so it is a candidate only.
- **When two or more screens host the same sheet, the glue is one hook, and the sheet state keeps a snapshot of its target.** `useEventSheet` (three screens) follows `useSeriesSheet` (two) so the sheets cannot drift, and `event-sheet.ts` stores the Event as it was when the sheet opened (D4-2), so a screen's refetch cannot blank or close the open sheet and the patch is computed against the snapshot.
