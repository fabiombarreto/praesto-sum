## Summary

This phase turns `tasks.priority` from a meaningless `integer` into a real
domain enum — `high | normal | low` — enforced the way every other domain enum
in this schema already is: a TypeScript union in `src/shared/api.ts` that the
Drizzle column reuses, plus a SQL `CHECK` the database itself refuses to
violate. The change is small in code and consequential in data: it produces
the project's first migration over real production data, so the generated SQL
is read before it is applied, `PRAGMA foreign_keys=OFF/ON` is rewritten as
`PRAGMA defer_foreign_keys` for D1, and the `tasks` table is dumped to a local
file before any remote apply. Because the create route currently forwards
`input.priority` unvalidated, the same phase must teach `POST /api/tasks` to
reject a non-enum priority with 400 — otherwise the new CHECK would surface as
a 500 instead of a validation error.

## Problem Statement

`priority` has been a column since the 2026-08-03 scaffold
(`src/worker/db/schema.ts:158`) and is the only domain enum in the schema not
enforced twice: it is `integer("priority")` with no CHECK, no documented scale,
and no interface that has ever written to it — the column is 100% NULL. An
integer whose meaning lives only in a comment is exactly the drift the
project's "enforced twice" pattern exists to prevent, and every unit that reads
Tasks from unit 2 onward would inherit it. The wire contract compounds the
problem: `TaskDto.priority` is typed `number | null` (`src/shared/api.ts:26`),
so the shape the eleven downstream consumers freeze against would be wrong from
the first read.

## Solution Statement

Declare the canonical scale once, in `src/shared/api.ts`, as
`TaskPriority = "high" | "normal" | "low"` with a `TASK_PRIORITIES` list and an
`isTaskPriority` guard — mirroring `TaskStatus` / `TASK_STATUSES` /
`isTaskStatus` exactly. Retype the Drizzle column to
`text("priority", { enum: [...] })` and add a `tasks_priority_chk` CHECK next
to the existing `tasks_status_chk`, so the database enforces the same set. Let
`src/worker/dto.ts` carry the new type outward untouched — it already builds
the DTO field-by-field from the schema row type, which is what makes this a
compile-time change rather than a runtime surprise. Teach `POST /api/tasks` to
reject a non-enum priority with 400, using the same shape the route already
uses for an unknown `?status=`. Generate the migration with drizzle-kit, read
the SQL, rewrite the D1-hostile PRAGMA, and apply it locally; the remote apply
is a gated owner-run step documented in the deploy runbook (see `## Notes`).

## Patterns to Mirror

```ts

```

The column shape to copy for `priority` — with two deliberate differences:
priority is nullable (`NULL` means "not set", per the PRD Decisions Log) and
therefore carries neither `.notNull()` nor `.default(...)`. Copied by Task 2.

```ts
# SOURCE: src/worker/db/schema.ts:199-202
    check("tasks_title_not_empty", sql`length(trim(${t.title})) > 0`),
    check("tasks_status_chk", sql`${t.status} in ('open','done','missed')`),

    check("tasks_single_date_chk", sql`${t.deadline} is null or ${t.scheduledDate} is null`),
```

The CHECK half of the "enforced twice" rule. `tasks_priority_chk` is written
in the same list, in the same `<column> in (...)` shape, with an explicit
`is null or` clause because the column is nullable. Copied by Task 2.

```ts
# SOURCE: src/shared/api.ts:15,47-51

export const TASK_STATUSES: readonly TaskStatus[] = ["open", "done", "missed"];

export function isTaskStatus(value: unknown): value is TaskStatus {
  return typeof value === "string" && (TASK_STATUSES as readonly string[]).includes(value);
}
```

The union + frozen list + type-guard triple. `TaskPriority`,
`TASK_PRIORITIES` and `isTaskPriority` are written in exactly this shape and
in the same file. Copied by Task 1.

```ts
# SOURCE: src/worker/routes/tasks.ts:19-22
  const status = c.req.query("status");
  if (status !== undefined && !isTaskStatus(status)) {
    return c.json({ error: `Unknown status: ${status}` }, 400);
  }
```

The reject-unknown-enum-value shape: guard, 400, message naming the offending
value, nothing written. Copied by Task 4 for the create route's `priority`.

```ts
# SOURCE: src/worker/dto.ts:10-25

    id: row.id,
```

The mapping point that must NOT change. `row.priority` becomes
`TaskPriority | null` automatically once the schema column is retyped, and the

Referenced (not edited) by Task 1 and Task 2.

## NOT Building (Scope Limits)

- **`PATCH /api/tasks/:id`.** The update route is PRD phase 2. This phase
  makes a *valid* priority storable and an *invalid* one rejectable; it does
  not add an edit route.
- **A priority control in the UI.** Phase 4 owns the detail screen.
- **Ordering or filtering by priority.** The urgency ordering is phase 3;
  filter UI is unit 3. Nothing here reads priority back for sorting.
- **`recurrenceSeries.priority`.** The series template carries its own
  `priority: integer("priority")` (`src/worker/db/schema.ts:94`), also 100%
  NULL and also untyped. The PRD's Phase Details scope this phase to "the
  schema column" (singular) and its Evidence cites only
  `src/worker/db/schema.ts:158`, so widening the migration here would exceed
  the approved scope. Recorded in `## Risks and Mitigations` as a known
  inconsistency for unit 9 (recurrence) to resolve.
- **Authoring or editing test files.** Under `tdd: true` the test suite for
  this phase is authored by the `test-writer`/`test-reviewer` pair before the
  Implementer runs, and R-X strict forbids the Implementer from touching a test
  file. No task here edits `test/`; Task 5 runs the suite, it does not write it.
- **Backfilling existing rows.** There is nothing to backfill — the column is
  100% NULL, which is the whole basis on which the owner accepted running this
  migration before chore C6 exists.
- **`updatedAt` or `detached` on the wire.** Both are deliberately unexposed
  per the PRD Decisions Log.

## Validation Commands

**Level 1 — STATIC_ANALYSIS**

```bash
set -euo pipefail
npm run check
```

`npm run check` is `wrangler types --check && tsc -b && eslint . && prettier --check .`
(`package.json`). Each stage exits non-zero on failure and `&&` propagates, so
the block fails on any of them. This is where a missed retype surfaces: with
`TaskDto.priority` still `number | null`, `src/worker/dto.ts:18` stops
compiling.

**Level 2 — UNIT/INTEGRATION TESTS**

```bash
set -euo pipefail
npx vitest run --project worker
npx vitest run --project docs
```

`vitest run` exits non-zero when any test fails — no output parsing, no
guessed reporter format. The `worker` project applies `migrations/` into an
ephemeral D1 before the suite (`test/apply-migrations.ts:10`), so a broken
migration fails here rather than in production.

**Level 3 — FRESH-DATABASE END-TO-END**

```bash
set -euo pipefail
npm run db:migrate
npm test
if grep -rn "PRAGMA foreign_keys" migrations/; then
  echo "FAIL: a D1-hostile PRAGMA foreign_keys statement remains in migrations/"; exit 1
fi
if npx wrangler d1 execute praesto-db --local --command \
     "INSERT INTO tasks (id, title, priority) VALUES ('plan-check', 'CHECK probe', 'urgent')"; then
  npx wrangler d1 execute praesto-db --local --command \
    "DELETE FROM tasks WHERE id = 'plan-check'"
  echo "FAIL: the tasks_priority_chk CHECK accepted an out-of-enum value"; exit 1
else
  echo "PASS: the database refused priority 'urgent'"
fi
```

The last probe is the load-bearing one: it asserts the database itself, not
just TypeScript, refuses `'urgent'`. `wrangler d1 execute` exits non-zero when
the statement is rejected, so the `then` branch runs only when the CHECK
failed to fire — and that branch cleans up the row it should never have
written, then exits 1. The `if` wrapper is what keeps `set -e` from treating
the intended rejection as a block failure.

## Acceptance Criteria

- **AC-A1 (PRD AC-4):** `tasks.priority` is `text("priority", { enum: ["high", "normal", "low"] })`
  and the table carries a `tasks_priority_chk` CHECK, so a direct SQL insert of
  any other non-NULL value is rejected by the database.
- **AC-A2 (PRD AC-4):** `src/shared/api.ts` exports `TaskPriority`,
  `TASK_PRIORITIES` and `isTaskPriority`, and both `TaskDto.priority` and
  `CreateTaskInput.priority` are typed `TaskPriority | null`; the file still
  imports nothing.
- **AC-A3 (PRD AC-4):** `POST /api/tasks` with `priority` of `high`, `normal`
  or `low` returns 201 and stores it; with any other value it returns 400 and
  writes nothing; with `priority` omitted or `null` it returns 201 and stores
  `NULL`.
- **AC-A4 (PRD AC-7):** the list, complete, reopen and delete routes keep their
  paths, behaviour and response bodies — every pre-existing assertion in
  `test/tasks.test.ts` passes without being edited.
- **AC-A5 (PRD AC-4):** the migration is drizzle-kit-generated into
  `migrations/`, contains no `PRAGMA foreign_keys` statement, and applies
  cleanly to a fresh D1 built from `migrations/` alone.
