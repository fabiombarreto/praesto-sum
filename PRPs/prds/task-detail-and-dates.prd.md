## Problem Statement

Capture works. Unit 1 made it take seconds from any app, and the owner now
records things he previously forgot. But a Task captured in three seconds while
walking is, by construction, a rough Task: a title with a typo, no date, no
sense of whether it matters. Today Praesto offers exactly three things to do
with it afterwards — complete it, reopen it, delete it. There is no way to
*correct* it.

The consequence is not cosmetic. A Task that cannot be fixed is a Task the
owner deletes and retypes, which is slower than never having captured it, or
one he leaves wrong, which quietly erodes trust in the list. Worse, the fields
that make a Task actionable — *when* it must happen, and whether it matters —
already exist in the database and are reachable by nothing. `deadline`,
`scheduledDate`, `description` and `priority` have been columns since the
2026-08-03 scaffold and no interface has ever written to them.

There is a second problem, invisible to the owner and expensive to everyone
downstream: **the Task wire contract has one consumer today and eleven more by
the end of the roadmap.** Units 3, 5, 8, 9, 10, 11, 13, 14 and 20 all read
Tasks. Whatever shape this unit leaves behind is the shape they inherit, and
changing it later means changing every one of them at once.

## Evidence

- **Roadmap, unit 2 exit signal:** "A Task created in a hurry was later
  corrected (title and date) instead of deleted and recreated." Deleting and
  recreating is the failure mode this unit exists to remove.
- **Roadmap, "Notes on five positions":** "Unit 2 is the contract-freeze
  point. The Task wire contract has one consumer today and many by the end of
  this table. Its PRD designs the final shape (fields, filters, paging), not
  just what that screen needs."
- **The schema is already ahead of the API.** `src/worker/db/schema.ts:144-216`
  defines `description`, `deadline`, `scheduledDate`, `priority`, `lifeAreaId`,
  `detached` and `updatedAt`, with `tasks_single_date_chk` already enforcing
  deadline XOR scheduled date at the database level.
- **No update route exists.** `src/worker/routes/tasks.ts` serves create, list,
  complete, reopen and delete. There is no `PATCH`, so FR-002 ("edit any
  attribute") is at 0%.
- **The read contract is one filter wide.** `listTasks` accepts `?status=` and
  nothing else (`src/app/api.ts`); `TaskDto` exposes no ordering guarantee.
- **Priority has no meaning.** `priority` is `integer("priority")` with no
  CHECK and no documented scale — the only domain enum in the schema not
  enforced twice, and the only one no code has ever written.
- **Owner, 2026-08-12 (this PRD's Foundation round):** three priority levels;
  title corrected inline in the list with everything else on a detail screen;
  list ordered by date urgency; deadline vs scheduled date chosen explicitly;
  and the priority migration runs now rather than waiting for unit 5.

## Proposed Solution

Four changes, API-first, in the order the project's delivery discipline
requires (routes and tests green before any UI):

1. **Priority becomes a real domain enum.** `high | normal | low`, enforced by
   a TypeScript union *and* a SQL CHECK, replacing the meaningless integer.
2. **A Task can be edited.** One `PATCH /api/tasks/:id` route covering every
   editable attribute, with the deadline-XOR-scheduled rule and the ADR-0006
   `detached` rule honoured at the write boundary rather than in the UI.
3. **The read contract is frozen.** A documented ordering (urgency first), a
   documented filter vocabulary, and an explicit, recorded decision about
   paging — designed for the eleven consumers ahead, not for one screen.
4. **The owner can reach it.** Title corrected in place in the list; every
   other field on a detail screen one tap away.

## Key Hypothesis

We believe that **making a captured Task correctable in one tap** will turn
quick capture from a rough draft into a system the owner trusts. We will know
we are right when **he corrects Tasks instead of deleting and retyping them**,
and when dated Tasks start appearing — because a date is only worth setting if
the thing that holds it is worth keeping.

The leap of faith is that correction is the missing step. If the owner instead
never revisits a captured Task at all, no edit screen fixes that — that is a
*delivery* problem, and it belongs to unit 3 (today view) and units 6/7 (push).
This is recorded so a disappointing result is read correctly.

## What We're NOT Building

- **Filtering and the today view.** FR-007 belongs to unit 3. This unit
  *freezes the contract* those filters will speak, and implements the ordering;
  it does not build the filter UI.
- **Life Area assignment.** FR-008 is unit 13. `lifeAreaId` stays in the
  contract because the column and the DTO field already exist; nothing in this
  unit writes it.
- **Recurrence.** FR-009 is unit 9. This unit honours the `detached` rule so
  unit 9 does not have to retrofit it, and touches nothing else.
- **Reminders on a Task.** FR-025 (Task side) is unit 7.
- **Undo of an edit.** Attractive, and genuinely out of scope: it needs an
  edit history table nothing else wants yet. Deleting is already undoable only
  by retyping, and that has not hurt.
- **Bulk editing.** One user, a few hundred Tasks; selecting many and editing
  them together is a volume problem the owner does not have.
- **Natural-language dates ("next Friday").** Explicitly out of scope per the
  requirements' own "Out of scope for now" list, which parks NL capture until
  after the MVP.

## Acceptance Criteria (test scenarios)

- **AC-1 edit-persists:** Given an existing Task, when the owner changes its
  title, description, date or priority, then the change is persisted and
  returned, and every field he did not touch is unchanged.
- **AC-2 partial-update-is-explicit:** Given a `PATCH` body, when a field is
  *omitted*, then that field is left as it was; when a field is sent as
  `null`, then it is cleared. Omission and clearing are distinguishable.
- **AC-3 dates-stay-exclusive:** Given a Task carrying a deadline, when a
  scheduled date is set, then the deadline is cleared in the same write, so
  the Task never holds both and the write never fails the CHECK.
- **AC-4 priority-is-an-enum:** Given a `PATCH` carrying a priority, when the
  value is `high`, `normal` or `low`, then it is stored; when it is anything
  else, then the request is rejected with 400 and nothing is written.
- **AC-5 occurrence-edit-detaches:** Given a Task that belongs to a recurrence
  series, when any attribute of it is edited, then `detached` becomes true, so
  a later series edit cannot silently overwrite the owner's correction.
- **AC-6 urgency-ordering:** Given Tasks with mixed dates, when the list is
  read, then they come back overdue first, then today, then future by date
  ascending, then undated last — and the order is produced by the API, not by
  the client.
- **AC-7 completion-and-deletion-unchanged:** Given the existing complete,
  reopen and delete routes, when this unit ships, then their behaviour and
  their responses are byte-identical to before it.
- **AC-8 title-corrected-in-place:** Given a Task in the list, when the owner
  corrects its title without opening the detail screen, then the correction
  persists.
- **AC-9 unknown-field-is-rejected:** Given a `PATCH` body carrying a field
  that is not editable (`id`, `status`, `createdAt`, `completedAt`,
  `seriesId`, `occurrenceDate`, `detached`), then the request is rejected
  with 400 rather than silently ignored.
- **AC-10 limit-is-honoured:** Given a list request carrying `?limit=N`, when
  it is served, then at most N Tasks come back and they are the first N in
  the AC-6 order — so the field that lets paging arrive later without
  reshaping the contract is real, not merely declared.

AC-8 is the only DOM-bound criterion and is verified manually, per
`documentation/40-engineering/testing-strategy.md`. AC-1 through AC-7, AC-9 and
AC-10 are API-level and are authored test-first.

## Open Questions

1. **When does paging become necessary?** Decided *not* to ship a cursor now
   (see Decisions Log). The trigger to revisit is the first list response over
   ~500 Tasks or over 100 KB, whichever comes first — measurable from the real
   table at any time.
2. **Should editing a `done` Task reopen it?** Today it stays `done`. Low
   stakes and genuinely unclear; to be answered by real use rather than
   decided now.
3. `TBD - needs validation`: whether "normal" is worth an explicit value at
   all, or whether the owner will only ever mark things `high` and leave the
   rest unset. If a month of real use shows `normal` is never chosen
   deliberately, the enum collapses to a flag and the CHECK narrows.

## Users & Context

**Primary user.** The owner, and only the owner (CON-002). Devices: an Android
phone and a Windows PC (CON-007), with the PWA installed on both since
2026-08-04 and a durable token since 2026-08-11.

**Job to Be Done.** When I look back at something I captured in three seconds
and it is wrong, incomplete or undated, I want to fix it where I am, in one
tap, so that the list stays worth reading instead of slowly filling with rough
notes I no longer trust.

**Trigger.** Two moments, and they are different. The first is immediately
after capture, when the owner notices the title is wrong — that is the inline
correction. The second is later, reviewing the list, when he decides *when*
something must happen — that is the detail screen.

### MVP Scope

A Task can be corrected and dated. That alone makes capture trustworthy, and
it is what the exit signal measures.

### User Flow

List → tap the title → correct it → it saves. Two interactions, no navigation.

List → tap the Task → detail screen with description, "complete by" / "do on",
and priority → change → back. The date control makes the choice explicit
rather than inferring it.

## Technical Approach

### Feasibility

**HIGH, with one deliberate exception.** Every editable field already exists as
a column, the DTO already carries most of them, and the deadline-XOR-scheduled
invariant is already a CHECK. The exception is priority: turning it into a real
domain enum is the project's **first migration over real production data**, and
it is treated as such below.

### TDD Routing

Current value of `tdd` in `docs/context/methodology.md`: **true**. Test-first
ordering — the test pair (test-writer/test-reviewer) produces the initial test
suite from the Acceptance Criteria above, before the Implementer runs.

AC-1 through AC-7 and AC-9 are API-route and data-layer criteria, which
`documentation/40-engineering/testing-strategy.md` puts squarely on the
automated side. AC-8 is DOM-bound and is verified manually. Nothing in this
unit touches a browser API, so the extraction rule that governed unit 1 phase 2
does not apply here.

### Architecture Notes

- **Priority migration.** `priority` becomes
  `text("priority", { enum: ["high", "normal", "low"] })` with a matching
  CHECK, mirroring every other domain enum in the schema. The column is
  currently **100% NULL** — no interface has ever written to it — which is why
  the owner accepted running this before chore C6 exists (Decisions Log).
- **`PATCH` semantics.** The route distinguishes an omitted key from an
  explicit `null`. This is why the input type cannot reuse `CreateTaskInput`,
  whose optional fields already mean "absent".
- **Date exclusivity is resolved server-side.** Setting one date clears the
  other in the same statement, so the CHECK is never the thing that reports the
  conflict to the owner. The CHECK stays as the structural backstop.
- **`detached` is written by the route, not the UI.** ADR-0006 gives it its
  meaning; unit 9 gives it its consumer. Honouring it now costs one line and
  saves unit 9 a retrofit over real data — the same reasoning the roadmap
  applies to unit 14 being "born sync-aware".
- **Ordering is computed by the API.** Sorting in the client would put the
  frozen contract's most load-bearing guarantee in the one place unit 3, unit
  8 and the export cannot reuse.
- **No Worker route is removed or renamed.** Create, list, complete, reopen and
  delete keep their paths and responses (AC-7).

### Technical Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| The migration damages real Task data | Low | The column being migrated is 100% NULL. The generated SQL is read before it is applied, per the Definition of Done, and any `PRAGMA foreign_keys=OFF/ON` is rewritten as `PRAGMA defer_foreign_keys`. Phase 1 additionally requires a manual dump of the `tasks` table to a local file before the remote apply — a two-minute stand-in for chore C5, which does not exist yet |
| The frozen contract turns out wrong and unit 3 needs to break it | Medium | The freeze is deliberately narrow: it fixes ordering, field names and types, and the omitted-vs-null rule. It does not fix filter *names*, which unit 3 may still add. Adding a field is backward-compatible; that asymmetry is what the freeze protects |
| `PATCH` semantics get muddled and clearing a date becomes impossible | Medium | AC-2 exists precisely for this and is authored test-first, with both the omission case and the explicit-null case as separate assertions |
| Priority's three levels prove to be the wrong shape | Medium | Open Question 3 names the collapse path (enum narrows to a flag) and the evidence that would trigger it. Cheap because the enum is enforced in one CHECK and one union |

### Phase Details

**Phase 1 — Priority as a domain enum.** Change the schema column, generate the
migration with drizzle-kit, read the generated SQL, and apply it locally then
remotely. Covers AC-4. **Before the remote apply, dump the `tasks` table to a
local file** (`npx wrangler d1 execute praesto-db --remote --command "SELECT *
FROM tasks"`, output kept off-repo): chore C5 does not exist yet, and this is
the cheapest honest substitute. The owner accepted this sequencing on
2026-08-12 knowing C6 has not run; the justification is that the column carries
no data to lose.

**Phase 2 — Task update route.** `PATCH /api/tasks/:id`. Covers AC-1, AC-2,
AC-3, AC-5, AC-9. The route owns three rules the client must never own: an
omitted key is not a `null`, setting one date clears the other, and editing an
occurrence detaches it. AC-7 is a standing obligation of this phase — the
existing routes are not touched.

**Phase 3 — Frozen read contract.** Ordering: overdue, then today, then future
ascending, then undated. Covers AC-6. This phase also writes down the parts of
the contract it does *not* implement — the filter vocabulary unit 3 will use
and the paging decision — because the roadmap makes this PRD responsible for
the final shape, and a shape recorded only in a future PRD is not frozen.

**Phase 4 — Detail screen and inline title edit.** Covers AC-8, verified
manually on both devices. Last, per the project's API-first delivery
discipline.
