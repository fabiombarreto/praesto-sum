## Candidate Decisions (for operator review)

The following were observed in the patch, the plan notes or the PRD but are inferred, owner-pending or not stated as a decision, so they were NOT written to `docs/decisions.md`, `docs/anti-patterns.md` or `docs/context/conventions.md` per the PRESERVE-ENTIRELY rule. Review and add manually if stable:

- **A multi-day or overnight event is listed on every day it covers, for Google as well as for the owner's own (plan decision D3-3).** The unit-4 rule listed a Google event on its start day only; `itemsInRange` and therefore *Hoje*'s Agenda now list it on each day from its start day through the day of its last instant (`end - 1`), so an event ending exactly at 00:00 does not spill onto the next day. The patch is explicit in code and headers, but no ADR or `documentation/` file records it, and PRD AC-23 says a Google-only day "looks exactly as it does today". Candidate: a PRD Decisions Log row or a new ADR (owner-owned; accepted ADRs are append-only, so ADR-0016 itself is not edited), stating the span rule and that it deliberately changes the unit-4 Agenda. See the second Deferred Question.
- **A "day" is always a day in the owner's zone, for every source (plan decision D3-1).** An all-day date is used verbatim; a timed instant is converted with `PRAESTO_TIMEZONE`, and an Event's own `timezone` never moves it to another day. Companion to the phase 2 candidate that `America/Sao_Paulo` has had no DST since 2019: both assume a single fixed owner zone. Candidate for `docs/context/constraints.md` or ADR-0016's follow-up: the day-grouping zone is the owner's, not the Event's.
- **An Agenda or day view must never read as free while a source has not answered (the unit's success metric made code).** `decideAgendaNotice` speaks the empty text only with no rows AND every other source answered; `partial` and `failed` always speak; `loading` says nothing; `DayScreen` and *Hoje* both show a failed non-Google source as a line of its own. Candidate anti-pattern for `docs/anti-patterns.md` ("Letting a failed or unanswered source read as an empty day"). Not written in: the file's header says nothing there is inferred and every entry comes from an owner-approved ADR or validated convention, and this rests on a code header and the PRD's success metric.
- **A row whose action does not exist yet carries no control, role, tabIndex or pointer/hover styling (plan decision D3-5).** `LocalEventRow` is inert until phase 4 so that nothing invites a tap that does nothing. Candidate for the UI/UX guidelines in `documentation/40-engineering/ui-ux-guidelines.md` (owner-validated; not a `docs/` edit). If it is a rule, phase 4 must remove the inertness in the same change that adds the sheet.
- **One adapter closes a unit mismatch.** `EventDto` stores epoch seconds and `CalendarEventDto` milliseconds; `dayItemPlacement` is the single place the range function converts, and `dayItemFromLocalEvent` scales the start once more, for its own `dueDate`, applying the same owner-zone rule (the attempt-1 review flagged a comment that claimed otherwise, and attempt 2 corrected it). Candidate convention: any future source with a third unit goes through `dayItemPlacement`; and if the two start-day conversions ever diverge, both must change.
- **A screen that stays mounted across a prop change resets its state in the render that first sees the new prop and drops late responses by a per-source counter plus the day they were issued for.** This is the pattern `DayScreen` documents in its header (React's "adjust state when a prop changes" idiom, and `App.tsx` giving it no `key`). Candidate convention for `docs/context/conventions.md` if a second screen needs it (unit 16's week view is the likely one); one instance is not yet a convention.
- **Carried over from the phase 1 and 2 manifests, still open:** the four-character non-blank CHECK idiom, the two coexisting wall-clock-to-instant functions with different DST-gap semantics, the `EventRow`/`NewEventRow` naming, the Web API globals inside `src/shared/` (phase 3 adds one more instance of the existing `format.ts` precedent: `day-view.ts` uses `Intl.DateTimeFormat` and `Date`, both available in the Worker and browser targets, and `day-range.ts` states it uses `new Date(<number>)` only), `formatVersion` staying 1 when only keys are added, the server-side versus client-side two-character search floor, the ambient-clock UTC offset on the `q`-only sort, the closed-key allowlist on `POST`, and the `PATCH` end-does-not-move semantics.
