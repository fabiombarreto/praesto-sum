## Problem Statement

Praesto cannot yet act on its own: `scheduled()` in `src/worker/index.ts:46-61` is a documented
stub, so with the app closed nothing reaches the owner. Worse than being absent, the channel is
**silent when it breaks** — a notification that never arrives is indistinguishable from one nobody
sent, so building unit 7 `reminders` on an unproven channel would make every future delivery bug
undiagnosable. The cost of not solving it is that milestone M2 ("the assistant acts on its own")
rests on an assumption instead of a proof.

## Evidence

- `src/worker/index.ts:46-61` — `scheduled()` is empty, carrying a comment that names the two jobs
  the project's MVP phase owes (due-Reminder scan → Web Push dispatch; recurrence sweep). Only the
  dispatch half is this unit's; the scan belongs to unit 7. `wrangler.jsonc` already
  fires it every 5 minutes.
- `docs/domain/areas/reminders.md:16` states the requirement in the project's own words: *"Push
  failure is SILENT — the dedicated VAPID integration test is mandatory, and a manual test-push
  route is recommended."*
- `src/sw.ts:49-102` already implements `push` and `notificationclick` end to end (payload parse,
  `showNotification` inside `waitUntil`, `clients.matchAll` → `focus()` else `openWindow()`, plus a
  `NOTIFICATION_CLICK` deep-link `postMessage`). The client half of the channel exists; the server
  half does not.
- `src/worker/db/schema.ts:272-289` already declares `push_subscriptions` (unique `endpoint`,
  `p256dh`, `auth`, `deviceLabel`, `createdAt`, `lastSeenAt`), created in
  `migrations/0000_neat_the_fallen.sql`. No migration is needed to store subscriptions.
- Chore C4 (2026-09-07, commit `0d5493f`) put `VAPID_SUBJECT`, `VAPID_PUBLIC_KEY` and
  `VAPID_PRIVATE_KEY` in `.dev.vars` and in the Worker's production secrets, with
  `scripts/generate-vapid.mjs` for rotation. Key generation is out of this unit's scope.
- Codebase research found **no** `web-push` send call, no subscription route, no diagnostics
  endpoint, no client-side `PushManager.subscribe`, no cron-run table, and no test referencing
  push or VAPID. The whole server side and the whole settings surface are greenfield.

## Proposed Solution

Build the server half of a Web Push channel and make its liveness observable, without touching
Reminders (unit 7's scope). Concretely: prove first that a push can actually leave workerd
(a spike, because the send library is in doubt — see Technical Risks); then a subscription
lifecycle in `src/shared` behind a port with routes to subscribe, unsubscribe and fire a manual
test push; then a `scheduled()` that stops being a stub by recording every run into a `cron_runs`
table that a bearer-gated diagnostics endpoint reads; then the `/settings` → *Notificações* route
carrying the two-step permission flow, the toggle, the "bloqueadas" state and the diagnostics
sub-page. The alternative — going straight to unit 7 and letting Reminders prove the channel —
was rejected because it conflates two failures (no reminder fired vs. the push was lost) into one
symptom, which is exactly the diagnosis problem this unit exists to remove.

## Key Hypothesis

We believe a proven push channel plus a diagnostics screen will let the owner trust that Praesto
acts while the app is closed, and let him tell a dead channel from an idle one without reading
logs. We'll know we're right when his Android phone rings with the app closed and the diagnostics
screen tells him, in one glance and without interpretation, that the cron ran less than 10 minutes
ago.

## What We're NOT Building

- **The due-Reminder scan.** Unit 7 `reminders` owns it. `scheduled()` here records that it ran; it
  reads no Reminder and sends no scheduled notification of its own.
- **Snooze, re-fire, and notification actions.** Resolved 2026-08-03 in
  `docs/domain/areas/reminders.md`: not in the MVP; the notification opens the app on the item and
  rescheduling is manual.
- **A fallback channel (e-mail-to-self, ntfy).** Pre-authorized by ADR-0003 without a new ADR, but
  only warranted if Web Push proves unreliable in real use — which is what this unit measures.
  Recorded as an Open Question.
- **A browser test tier (Playwright / Vitest browser mode).** See the Decisions Log; the roadmap
  backlog trigger fired here and the answer is a recorded rejection, not a silent skip.
- **Multi-device fan-out policy.** The subscription table already supports many rows; this unit
  ships the lifecycle, not a strategy for choosing among several devices.
- **Rich notification content beyond the guidelines.** `ui-ux-guidelines.md` §8 already fixes title,
  body, icon, badge, `tag` and tap behaviour. This unit implements that row; it does not re-open it.

## Acceptance Criteria (test scenarios)

- **AC-1 Payload shape:** Given a notification request with a title longer than 30 characters and a
  target route, when the payload is built by `src/shared`, then the emitted object carries the title
  truncated to the 30 visible characters of `ui-ux-guidelines.md` §8, a body stating when and what,
  the mark as icon, the monochrome 72 px badge, a `tag` derived from the target's identity, and the
  target route under `data` — and it never carries more than 2 actions.
- **AC-2 Subscription identity is the endpoint:** Given a subscription for an endpoint already
  stored, when it is submitted again with different keys, then the existing row is updated in place
  (keys and `lastSeenAt` refreshed) and the row count is unchanged — the unique `endpoint` index of
  `src/worker/db/schema.ts:272-289` is the invariant, not a convention.
- **AC-3 Dead endpoints are pruned:** Given a push service response of 404 or 410 for an endpoint,
  when the outcome is mapped, then the result classifies that endpoint as gone and exactly that row
  is deleted; given 201, the result is success and nothing is deleted.
- **AC-4 Transient failures are not pruned:** Given a push service response of 429 or any 5xx, when
  the outcome is mapped, then the result classifies it as retryable, the subscription row survives,
  and the failure is recorded with its status code — a transient error never silently discards the
  owner's only subscription.
- **AC-5 Every cron run is recorded:** Given the cron fires, when `scheduled()` completes, then a
  row exists in `cron_runs` carrying the start instant, the outcome and the duration; and given the
  job body throws, then a row still exists carrying the failure — a crashed run is recorded, never
  absent.
- **AC-6 Freshness classification at the 10-minute threshold:** Given a last-run instant and a
  reference instant, when `src/shared` classifies cron health, then a gap under 10 minutes is
  `fresh`, a gap of 10 minutes or more is `stale`, and no recorded run at all is `unknown` —
  three distinct states, never `stale` standing in for `unknown`.
- **AC-7 Diagnostics endpoint is bearer-gated and complete:** Given a request without a valid bearer
  token, when the diagnostics endpoint is called, then it answers 401 and no body; given a valid
  token, then the response carries the last cron run instant, its outcome, the derived freshness
  state, the number of stored subscriptions, and the last push dispatch attempt with its status.
- **AC-8 Manual test push reports its outcome:** Given at least one stored subscription, when the
  test-push route is called with a valid token, then the response names, per endpoint, whether the
  push service accepted it and with which status code; and given zero stored subscriptions, then the
  response says so explicitly rather than reporting a vacuous success.
- **AC-9 Permission flow is a two-step state machine:** Given notification permission is `default`,
  when the *Notificações* route renders, then it shows the explainer and the enabling control, and
  no permission prompt has fired; given the owner taps the control, then and only then is the real
  prompt requested; given permission is `denied`, then the screen shows the "bloqueadas" state with
  the way back and offers no control that would silently do nothing.
- **AC-10 The phone rings with the app closed (device pass, manual):** Given the PWA is installed
  and closed on the owner's Android phone and a subscription is stored, when a push is dispatched,
  then the phone shows the notification, and tapping it opens Praesto on the route carried in the
  payload. *Verified by the owner on his device and recorded in the phase report — no automated
  tier can assert this (see the Decisions Log).*
- **AC-11 The send-library verdict is recorded, not just reached:** Given the phase-1 spike has run,
  when the repository is inspected, then exactly one send library is named as adopted with an exact
  version pin (no `^`/`~`), the PRD's Decisions Log "Send library" row carries the verdict and states
  that it was settled by running the library inside workerd rather than by reading about it, and — if
  the adopted library is not `web-push` — an ADR exists that supersedes ADR-0005's naming of it. A
  spike that reaches a conclusion nobody wrote down leaves the next reader to re-run it.

## Users & Context

**Primary User**
- **Who:** The owner — sole user, developer and operator of Praesto; Android phone, Windows PC,
  a ~1 h/day budget (CON-003).
- **Current behavior:** He opens the app to find out what needs doing. Nothing reaches him when it
  is closed, so anything time-bound still lives in his memory or in another tool.
- **Trigger:** The moment he stops watching the screen — the app is closed and a commitment is due.
- **Success state:** The phone rings without him asking, and when he doubts whether the assistant is
  alive he can check in one glance instead of opening `wrangler tail`.

**Job to Be Done**
When I close the app and get on with my day, I want Praesto to still be able to reach me — and to be
able to check that it can — so I can stop holding time-bound commitments in my head.

**Non-Users**
Anyone but the owner. There is no multi-user model, no shared inbox, no team notification policy,
and no per-user preference layer — a single subscription table for a single person.

## Solution Detail

### Core Capabilities (MoSCoW)

| Priority | Capability | Rationale |
|----------|------------|-----------|
| Must | A push actually leaves workerd and reaches the device | Everything else is decoration if this does not hold, and the send library is in doubt |
| Must | Subscribe / unsubscribe routes over the existing `push_subscriptions` table | Without a stored subscription there is nothing to send to |
| Must | Dead-endpoint pruning on 404/410, retention on 429/5xx | ADR-0003's data-safety posture applied to the channel: never discard the only subscription over a transient error |
| Must | `scheduled()` records every run into `cron_runs` | The diagnostics screen has nothing to show otherwise, and this is what stops the stub being a stub |
| Must | Bearer-gated diagnostics endpoint | Every `/api/*` route is gated; no exception |
| Must | `/settings` → *Notificações* route: explainer, toggle, "bloqueadas" state, diagnostics sub-page | `ui-layout-standard.md` §6 already assigns this shape to unit 6 |
| Must | Manual test-push route and its control on the screen | `docs/domain/areas/reminders.md:16` recommends it; it is the answer to silent failure |
| Should | `permissions.query({name:'notifications'})` `change` observation | `ui-ux-guidelines.md` §8 asks for it; the screen stays honest when permission changes outside the app |
| Should | Last dispatch attempt (status + instant) surfaced in diagnostics | Turns "it did not ring" into a readable cause |
| Could | A device label the owner can edit | Only earns its place with a second device |
| Won't | Due-Reminder scan, snooze, re-fire, notification actions, fallback channel | Unit 7's scope, or resolved/deferred above |

### MVP Scope

The channel end to end plus the means to judge it: subscribe, dispatch (manual and from the cron's
own heartbeat), prune, record, and one screen that reads it all back in pt-BR. No Reminder is read.

### User Flow

Owner opens `/settings` → taps *Notificações* → reads the explainer → taps *Ativar notificações* →
the real permission prompt fires inside that tap → he allows → the subscription is stored → he taps
*Enviar notificação de teste* → closes the app → the phone rings → he taps the notification →
Praesto opens on the target route. Later, in doubt, he opens *Notificações* → *Diagnóstico* and
reads "última execução: há 3 min".

## Technical Approach

**Feasibility:** MEDIUM — every piece is well-trodden except one, and that one (whether the send
library runs inside workerd) is unresolved and load-bearing, which is why phase 1 is a spike.

### TDD routing

Current value of `tdd` in `docs/context/methodology.md`: **true**. Test-first ordering — the test
pair (test-writer/test-reviewer) produces the initial test suite from the Acceptance Criteria above,
before the Implementer runs.

Note for the test pair: this project's `tsconfig` is strict with **`noUncheckedIndexedAccess`** and
**`exactOptionalPropertyTypes`** (`documentation/40-engineering/engineering-conventions.md`). Write
against those from the first line — in unit 5 two suites passed under vitest and only broke
`tsc -b` once the seam existed, and naming the flags up front was the recorded systemic fix.
AC-10 is a device pass and produces **no test file**; that is the sanctioned no-test-required path
of `docs/context/methodology.md`, not a coverage gap.

### Architecture Notes

- **The client half already exists.** `src/sw.ts:49-102` handles `push` and `notificationclick`
  including the deep-link `postMessage`. Treat it as the contract the server payload must satisfy
  (AC-1), and change it only if the spike proves it must.
- **No migration for subscriptions.** `push_subscriptions` is already in `schema.ts` and in
  migration `0000`. One new table, `cron_runs`, needs a drizzle-kit-generated migration applied by
  `wrangler d1 migrations apply` — never `drizzle-kit migrate/push`.
- **The port/adapter split is mandatory, not stylistic.** Payload construction, outcome mapping and
  freshness classification go into `src/shared` (mirroring `src/shared/google-settings.ts` and
  `src/shared/request-failure.ts`); only the lines that call `PushManager`, `Notification` and the
  push service are the exempt thin adapter. This is what makes AC-1..AC-6 testable inside workerd,
  where there is no Notification API and no service-worker registration.
- **Settings card pattern.** `SettingsScreen.tsx:105-106` composes independent cards; the new work
  follows the `GoogleConnectionCard` + `src/shared/google-settings.ts` precedent — a pure reducer
  beside a glue component. Copy in pt-BR, mirroring the existing two cards' idiom (ADR-0009).
- **DTO discipline.** `src/shared/api.ts` declares wire types by hand and `src/worker/dto.ts` maps
  schema rows to them so a column rename breaks the build. The push-subscription and diagnostics
  DTOs follow that split; instants cross the wire as epoch seconds.
- **`userVisibleOnly: true` is mandatory in Chrome**, so every push must show a notification. That
  aligns with the §8 rule of one notification per firing; there is no silent-data-push option to
  design around.

### Technical Risks

| Risk | Likelihood | Mitigation |
|------|------------|------------|
| `web-push@3.6.7` does not run in workerd — the library depends on `https.request` and Node's `crypto.createECDH()`, neither available under `nodejs_compat` ([web-push#718](https://github.com/web-push-libs/web-push/issues/718)), while Cloudflare's own guide still recommends it ([docs](https://developers.cloudflare.com/agents/guides/push-notifications/)). It is a runtime dependency here but has only ever executed in Node, inside `scripts/generate-vapid.mjs` | H | Phase 1 is a spike that answers it by running it. If it fails, swap to a Web Crypto implementation (`@block65/webcrypto-web-push` is the named candidate, its README unverified — npm returned 403 to research) pinned exact, and record an **ADR**, because ADR-0005 names `web-push` |
| Android Doze / battery optimization delays or drops delivery | M | The exit signal measures *arrival*, not latency. If a drop is observed in real use, ADR-0003 pre-authorizes a fallback channel without a new ADR |
| A malformed payload is delivered to the SW but never surfaces — the classic silent failure | M | AC-1 pins the payload shape test-first against what `src/sw.ts` actually parses; the test-push route makes one round trip observable on demand |
| Permission granted once and revoked later outside the app (Chrome auto-revokes low-engagement sites; installed apps exempt, Oct 2025) | L | AC-9's `permissions.query` `change` observation keeps the screen honest instead of showing a toggle that does nothing |
| The diagnostics screen reports a healthy cron while dispatch is broken | M | Diagnostics carries the **last dispatch attempt and its status**, not only the last run — the two are separate rows on the screen |

### Phase Details

**Phase 1: push-send-spike**
- **Goal:** Answer the one question that can invalidate the other three phases.
- **Scope:** A minimal dispatch path from inside workerd to a real subscription, exercised in local
  dev; a written verdict on `web-push` under `nodejs_compat`; an ADR if the library changes; exact
  version pin for whatever is adopted.
- **Success signal:** A push sent from workerd reached the owner's device once, and the repo names
  the library it will use with the reason recorded.

**Phase 2: subscription-lifecycle**
- **Goal:** Store, refresh and prune subscriptions, and make one dispatch observable on demand.
- **Scope:** `src/shared` payload builder (AC-1) and outcome mapper (AC-3, AC-4); subscribe,
  unsubscribe and test-push routes behind the bearer gate; DTO mapping in `src/worker/dto.ts`;
  endpoint-identity upsert (AC-2).
- **Success signal:** `npm test` covers AC-1..AC-4 and AC-8; a test push fired from a route reaches
  the device; re-submitting the same endpoint leaves the row count unchanged.

**Phase 3: cron-heartbeat**
- **Goal:** Make the cron's liveness a fact stored in the database rather than an inference from
  logs.
- **Scope:** `cron_runs` table with a drizzle-kit migration; `scheduled()` recording start, outcome
  and duration including on throw (AC-5); persistence of the **last dispatch attempt** (instant +
  per-endpoint status) that AC-7 requires the diagnostics response to carry — phase 2 produces those
  outcomes, this phase is where they are stored; `src/shared` freshness classifier with the three
  states (AC-6); bearer-gated diagnostics endpoint (AC-7). No Reminder is read.
- **Success signal:** After a real cron tick in local dev, the diagnostics endpoint returns a
  `fresh` state with a run instant, and a deliberately throwing job body still produces a row.

**Phase 4: notifications-settings**
- **Goal:** Give the owner the screen that lets him enable the channel and judge it alone.
- **Scope:** A card on `/settings` plus the *Notificações* route with a diagnostics sub-page (routes
  with real history entries, per the layout standard); the two-step permission flow and the
  "bloqueadas" state (AC-9); the *Enviar notificação de teste* control; absolute + relative last-run
  time, the stale state above 10 minutes, subscription count with this device's status, and the last
  dispatch attempt with its status. pt-BR copy mirroring `GoogleConnectionCard` / `DataExportCard`;
  the `ui-ux-guidelines.md` review checklist run and its ✔/✘ result pasted in the phase record.
- **Success signal:** The owner reads the screen on his phone and can say whether the cron is alive
  without asking anyone — and AC-10's device pass is recorded in the phase report.

## Research Summary

**Market Context**
- Chrome mandates `userVisibleOnly: true`, forbidding silent data pushes — every delivery must show
  a notification ([MDN](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Tutorials/js13kGames/Re-engageable_Notifications_Push)).
- `web-push` is documented as broken inside Cloudflare Workers/workerd — `https.request` unsupported
  and `crypto.createECDH` missing even after `Buffer` polyfilling
  ([web-push#718](https://github.com/web-push-libs/web-push/issues/718)) — while Cloudflare's own
  push guide still recommends the package under `nodejs_compat` and shows 404/410 pruning with 5xx
  retry ([docs](https://developers.cloudflare.com/agents/guides/push-notifications/)).
  `@block65/webcrypto-web-push` is the named Web Crypto alternative; its README could not be
  verified (npm returned HTTP 403).
- The canonical `notificationclick` pattern is `clients.matchAll()` → compare URLs → `focus()`, else
  `openWindow()`, with the deep-link carried in `notification.data`
  ([Web Push Book](https://web-push-book.gauntface.com/common-notification-patterns/)) — which is
  what `src/sw.ts` already does.
- Web push delivery is not automatable in Playwright: `grantPermissions` rejects `push` on Chromium
  ([#5631](https://github.com/microsoft/playwright/issues/5631)); headless times out on the `show`
  event and headed shows no OS notification
  ([#23954](https://github.com/microsoft/playwright/issues/23954)); an independent repo confirms no
  working technique exists.
- "Silent" failures frequently originate in a malformed payload or a missing required field such as
  the title, rather than in delivery itself.
- **Gaps:** no source found within the search budget on Android Doze's effect on FCM-backed web push
  timing, nor on cron-heartbeat diagnostics patterns in small self-hosted apps (that focus area was
  not reached); whether `crypto.createECDH` has landed in a newer `nodejs_compat` release is
  unverified — which is precisely what phase 1 settles by running it.
