## Problem Statement

The owner's phone can ring, but nothing decides when. Unit 6 proved the Web Push
channel end to end on his own device, yet the only thing that fires a
notification today is a human tapping a test button in `/settings/notifications`.
Anything with a time — "drink water at 3pm" — or a deadline that needs warning
ahead of it — "tell me 1 h before this is due" — still lives in the owner's head
or in a phone alarm that knows nothing about his Tasks. That is the exact pain
the project exists to remove, and it is the difference between a channel that can
ring and an assistant that acts on its own.

## Evidence

- The roadmap's own reading of the state, written at unit 6's close: "a channel
  that can ring is not an assistant that decides when to" —
  `documentation/50-planning/roadmap.md:106`. Milestone **M2** is explicitly NOT
  reached until this unit lands.
- The code says the same thing about itself: `runScheduledJob` is an empty
  function whose doc comment reads "Intentionally empty placeholder: unit 7 will
  land the due-Reminder scan here. This phase reads no Reminder."
  (`src/worker/cron.ts:5-14`).
- FR-041 (*Must*, accepted) requires that a due Reminder produce a notification
  the owner actually perceives; FR-044 (*Must*) requires standalone Reminders;
  FR-025 (*Must*) requires attaching a Reminder to a Task at an absolute moment
  or relative to its deadline
  (`documentation/20-requirements/functional-requirements.md:58,72,75`).
- The `reminders` table has existed unused since migration `0000` — schema,
  `ReminderDto`, `toReminderDto` and export coverage are all in place
  (`src/worker/db/schema.ts:233-264`, `src/worker/dto.ts:115-126`,
  `src/worker/routes/export.ts:35-52`), while no route, no UI and no sweep read
  or write it. The data model has been waiting for the behavior.

## Proposed Solution

Give Reminders a full lifecycle and give the cron a job. Add an `/api/reminders`
CRUD router mirroring the hand-rolled validation style of
`src/worker/routes/tasks.ts`, covering both shapes the domain already allows: a
standalone Reminder (a label plus an absolute instant, FR-044) and a Reminder
attached to exactly one Task, set either absolutely or as an offset in minutes
before that Task's deadline (FR-025, Task side). Fill `runScheduledJob` with a
sweep over the existing `reminders_due_idx` that claims each due row with a
conditional `UPDATE ... WHERE sent_at IS NULL`, dispatches it through the
already-proven `sendPush` / `classifyPushOutcome` / `buildNotificationPayload`
path, and releases the claim only when the outcome is retryable — so a duplicate
is structurally impossible and a transient push failure still gets another tick.
Extend `AppRoute` with a per-Task route so the notification's `route` payload
lands on the item itself rather than on the home screen, and surface Reminder
creation and editing in the Task sheet and as a standalone entry point.

The alternative shapes were rejected for reasons the project has already
recorded. Computing fire times from a rule at sweep time is what ADR-0006's
denormalized `next_fire_at` exists to avoid, and that machinery belongs to units
9 and 17 — this unit stores absolute instants and scans them directly, exactly as
the table's own doc comment says it was designed to. Delegating delivery to
Google Calendar's reminders is forbidden by the ADR-0007 closed mirror inventory
and would double every notification. Client-side scheduling contradicts ADR-0003
and ADR-0004: the phone must ring with the app closed.

## Key Hypothesis

We believe a stored absolute `fire_at`, swept every five minutes by the Worker
cron and guarded by `sent_at` as a claim, will deliver reminders reliably enough
for the owner to stop keeping deadlines in his head and stop setting phone
alarms.

We'll know we're right when a full week passes in which every reminder arrived on
time — none duplicated, none silent.

## What We're NOT Building

- **Snooze and re-fire** — resolved on 2026-08-03: the notification opens the app
  on the item and rescheduling is manual. Notification-action snooze is a
  declared revisit trigger, not MVP scope.
- **Event Reminders (FR-025, Event side)** — unit 18. There is no Event entity in
  the schema yet; the `reminders.event_id` column is deliberately absent
  (`src/worker/db/schema.ts:20-21`).
- **Recurring Reminders and the ADR-0006 `next_fire_at` denormalization** — units
  9 and 17. This unit stores one absolute instant per Reminder and never expands
  a rule.
- **A new database table** — the `reminders` table already exists and is already
  in `EXPORTED_TABLE_NAMES` (`src/worker/db/export-manifest.ts:19`), so the unit
  5 export-completeness guard is not triggered.
- **Any fallback delivery channel (e-mail-to-self, ntfy)** — an open question in
  `docs/domain/areas/reminders.md`, permitted without a new ADR but not scoped
  here. Web Push is the channel unit 6 proved on the owner's real device.
- **Exactly-once delivery as a promise** — it is not achievable across a network
  boundary. The design chooses duplicate-free by construction and records
  precisely which failure can still produce silence (see AC-6 and the Technical
  Risks table).
- **Multi-user, sharing, or per-device reminder routing** — one owner; a Reminder
  goes to every registered subscription, as the test push already does.

## Acceptance Criteria (test scenarios)

- **AC-1 Standalone Reminder round-trip:** Given no Reminder exists, when
  `POST /api/reminders` receives `{ "label": "Beber água", "fireAt": <epoch
  seconds> }` with a valid bearer token, then a row is created with `taskId`
  null, `sentAt` null, and the response is the `ReminderDto` for it; a
  subsequent `GET /api/reminders` includes that row.
- **AC-2 Standalone Reminder must say what it is about:** Given a request body
  with no `taskId` and a `label` that is absent, empty, or whitespace-only, when
  `POST /api/reminders` is called, then the response is 400 with a pt-BR message
  and no row is written — the API rejects it before the database CHECK
  `reminders_label_chk` would.
- **AC-3 Reminder attached to a Task, relative to its deadline:** Given a Task
  with `deadline` `2026-09-20`, when a Reminder is created for it with
  `originOffsetMinutes: 60`, then `fireAt` equals the instant 60 minutes before
  the end of that local day in `America/Sao_Paulo` (`2026-09-20T23:59` local),
  and `originOffsetMinutes` is persisted as 60.
- **AC-4 A Reminder points at one target or none, never an unknown one:** Given a
  `taskId` that does not exist, when `POST /api/reminders` is called, then the
  response is 400 (or 404) with a pt-BR message and no row is written. Given a
  Task that is later deleted, when the deletion succeeds, then its Reminders are
  gone too (the existing `onDelete: "cascade"` on `reminders.task_id`).
- **AC-5 The sweep claims before it sends:** Given two Reminders whose `fireAt`
  is in the past and whose `sentAt` is null, when `runScheduledJob` executes,
  then each row's `sentAt` is set by a conditional update that matches only
  `sentAt IS NULL`, and `sendPush` is invoked at most once per row per run —
  a second `runScheduledJob` in the same window sends nothing.
- **AC-6 A retryable push outcome releases the claim; a delivered or gone one
  does not:** Given a due Reminder claimed by the sweep, when
  `classifyPushOutcome` reports a retryable outcome (429/5xx), then `sentAt` is
  reset to null so the next tick retries it; when the outcome is delivered, or
  `gone` for every subscription, then `sentAt` stays set and the row is never
  sent again.
- **AC-7 A dead subscription is pruned, and one dead endpoint does not suppress
  a live one:** Given two push subscriptions where one returns `gone` and the
  other succeeds, when the sweep dispatches a due Reminder, then the dead
  subscription row is deleted from `push_subscriptions` and the Reminder is still
  recorded as sent.
- **AC-8 The payload deep-links to the Task, not to the home screen:** Given a
  Reminder whose `taskId` is `T`, when the sweep builds its notification payload,
  then the payload's nested `{ data: { route } }` carries the path of Task `T`,
  and `routeFromPath` parses that path back into the corresponding `AppRoute`
  variant — `pathOf(routeFromPath(p)) === p` holds for it.
- **AC-9 A closed Task's Reminder does not ring:** Given a Reminder attached to a
  Task whose status is `done` or `missed`, when the sweep runs after its
  `fireAt`, then no push is dispatched for it and `sentAt` is set so it is not
  reconsidered on every subsequent tick.
- **AC-10 A Reminder that came due while the scheduler was down still fires
  once:** Given a Reminder whose `fireAt` is 40 minutes in the past and whose
  `sentAt` is null, when the sweep next runs, then it is dispatched exactly once
  — the sweep's predicate is `fireAt <= now AND sentAt IS NULL`, with no lower
  bound that would let a missed window swallow it silently.
- **AC-11 Editing a Task's deadline recomputes its relative Reminders:** Given a
  Task with `deadline` `2026-09-20` and a Reminder with `originOffsetMinutes:
  60`, when the Task's deadline is changed to `2026-09-25`, then that Reminder's
  `fireAt` moves to 60 minutes before the end of `2026-09-25` local, while a
  Reminder on the same Task with `originOffsetMinutes` null keeps its `fireAt`
  unchanged.
- **AC-12 An already-sent Reminder is not resurrected by an edit:** Given a
  Reminder whose `sentAt` is set, when its Task's deadline is edited, then the
  recomputation does not clear `sentAt` — a past notification is not re-delivered
  because a date moved.
- **AC-13 Every route stays behind the bearer gate:** Given a request to any
  `/api/reminders` route without a valid bearer token, when it is dispatched,
  then the response is 401 and no row is read or written (ADR-0003 safeguard 4).
- **AC-14 The offset-to-instant conversion is pure and clock-free:** Given the
  helper that converts a local `YYYY-MM-DD` plus an offset in minutes into an
  epoch instant, when it is called, then it reads no ambient clock, takes the
  timezone as an argument defaulting to `America/Sao_Paulo`, and lives in
  `src/shared/` — so `tsc -b` and the Vitest tier both cover it (the
  browser-API split recorded in `docs/context/methodology.md`).

## Users & Context

**Primary User**
- **Who:** the owner — sole user, on an Android phone with the PWA installed, and
  on a desktop browser.
- **Current behavior:** keeps timed intentions in his head, in scattered notes,
  or in native phone alarms that know nothing about his Tasks and do not survive
  a change of plan.
- **Trigger:** the moment he captures something that has a time ("drink water at
  3pm") or a deadline that needs warning ahead of it ("tell me 1 h before this is
  due").
- **Success state:** the phone rings at the right moment with the app closed, the
  notification names the thing, and tapping it lands on that thing.

**Job to Be Done**
When I record something that has a time or a deadline, I want the assistant to
warn me on its own, so I can stop carrying it in my head.

**Non-Users**
Anyone but the owner. There is no multi-user model, no sharing, no delegation,
and no notion of an audience for a Reminder. A Reminder is also not for anything
that needs to appear on someone else's calendar — the ADR-0007 mirror inventory
is closed and Reminders never leave Praesto.

### MVP Scope

The hypothesis is validated by the smallest system that can ring on its own: the
CRUD route for both Reminder shapes, the claim-before-send sweep with the
retryable release, the per-Task deep link, and enough UI to create and edit a
Reminder in pt-BR, plus the two correctness rules the acceptance criteria make
blocking: suppressing delivery for closed Tasks (AC-9, phase 2) and recomputing
relative fire times when a deadline moves (AC-11 / AC-12, phase 4). The only
Should item is the pending-Reminders view, which is the one capability with no AC
of its own — the exit signal is a week of correct deliveries, and the Must set
alone produces it.

### User Flow

1. The owner opens a Task and taps to add a reminder, choosing "1 hora antes do
   prazo"; or he adds a standalone reminder with a label and a time.
2. The client `POST`s to `/api/reminders`; the server resolves the offset against
   the Task's deadline into an absolute `fireAt` and stores the row. The screen
   shows the resulting date and time in words — no invisible arithmetic.
3. The cron fires within five minutes of `fireAt`, claims the row, and dispatches
   the push through the path unit 6 proved.
4. The phone rings with the app closed. The owner taps it and lands on that Task
   — the first non-`/` deep link this project has ever delivered to a device.

## Technical Approach

**Feasibility:** HIGH — the table, its scan index, the push dispatch functions,
the outcome classifier, the cron heartbeat and the permission screens all exist
and are proven in production. What is missing is the logic between them, plus one
genuinely new piece (the per-Task route).

### TDD routing

Current value of `tdd` in `docs/context/methodology.md`: **true**. Test-first
ordering — the test pair (test-writer/test-reviewer) produces the initial test
suite from the Acceptance Criteria above, before the Implementer runs.

Two notes the suite must respect, both recorded in
`docs/context/methodology.md`: React component verification stays manual, so the
UI phase legitimately produces no component test; and anything that could fail
silently belongs in `src/shared/` as a pure function so the Vitest-inside-workerd
tier can reach it. The offset-to-instant conversion (AC-14) and the route
codec (AC-8) are exactly that.

### Architecture Notes

- **No new table, no migration over real data.** `reminders` exists with
  `fire_at`, `sent_at`, `origin_offset_minutes`, the `reminders_due_idx` on
  `(sent_at, fire_at)` and the `reminders_label_chk` CHECK
  (`src/worker/db/schema.ts:233-264`). It is already in `EXPORTED_TABLE_NAMES`
  (`src/worker/db/export-manifest.ts:19`), so the unit 5 export-completeness
  guard does not fire. If planning discovers a column is genuinely missing, the
  three coupled export files must be planned as explicit deliverables in the same
  phase.
- **Claim-before-send, with an explicit release.** The literature offers
  at-least-once (send then mark: never silent, may duplicate) or at-most-once
  (mark then send: never duplicates, may go silent). The exit signal asks for
  both, which no single ordering gives. The chosen shape is mark-then-send plus a
  release on a retryable outcome: duplicates become structurally impossible, and
  the only remaining silence is a crash between the claim and the dispatch —
  which is not invisible, because `runCronHeartbeat` writes a `failure` row to
  `cron_runs` from its `finally` block (`src/worker/cron.ts:29-51`). The PRD says
  this rather than promising exactly-once.
- **Absolute instants only.** `fire_at` is stored in UTC epoch seconds and
  scanned directly. No rule expansion on the hot path — that is what the table's
  own doc comment was written for, and what ADR-0006's `next_fire_at` will serve
  in units 9/17.
- **The deadline needs a time of day.** A Task carries only a local calendar day
  (`deadline` / `scheduled_date` as `YYYY-MM-DD`), so "1 h before the deadline"
  has nothing to count back from. The convention is end-of-day local (23:59 in
  `America/Sao_Paulo`), expressed as a single named constant in `src/shared/`,
  with the computed instant shown to the owner before saving. Todoist refuses
  relative reminders on date-only tasks for exactly this reason; Praesto answers
  the question instead of refusing, and makes the answer visible.
- **The per-Task route is new work, not a device-proof of existing work.**
  `AppRoute` today is `"today" | "settings" | "notifications" |
  "notifications-diagnostics"` (`src/shared/app-route.ts:25`) — there is no Task
  variant at all. `routeFromPath`, `pathOf`, the payload builder, the `sw.ts`
  `notificationclick` handler and the SPA's `postMessage` listener all need to
  learn it. The roadmap's residual ("built and unit-tested but not
  device-proven") understates this; the PRD corrects it.
- **Reuse, do not re-implement, the dispatch path.** `sendPush`,
  `classifyPushOutcome` and `buildNotificationPayload` are called by
  `POST /api/push/test` (`src/worker/routes/push.ts:127-144`), including the
  prune-on-`gone` behavior confirmed against real FCM in production. The sweep
  calls the same three.
- **Mirror the house route style.** `src/worker/routes/tasks.ts` uses hand-rolled
  validation with a local `readJson` guard, `Object.hasOwn` for partial updates,
  explicit 400s, and DTO mapping only at the response boundary. No zod, no new
  validation dependency.
- **Name `noUncheckedIndexedAccess` and `exactOptionalPropertyTypes` at the exit
  gate.** This project has twice had a suite pass under Vitest and break under
  `tsc -b`; the sweep indexes query results and the DTO carries optional fields,
  which is where both bite. `npm run check` is part of the definition of done for
  every phase, not a final flourish.

### Phase Details

**Phase 1: Reminder API and the time contract**
- **Goal:** every Reminder the domain allows can be created, read, corrected and
  removed through a token-gated route, and "1 h before the deadline" has a single,
  tested, clock-free definition.
- **Scope:** `src/worker/routes/reminders.ts` mounted in the `/api/*` router;
  write-side request/response types added to `src/shared/api.ts` flowing from
  `schema.ts` through `dto.ts`; validation mirroring `tasks.ts` (both Reminder
  shapes, unknown `taskId`, empty label, malformed instants); the pure helper and
  the end-of-day constant in `src/shared/`. No UI, no cron.
- **Success signal:** AC-1, AC-2, AC-3, AC-4, AC-13 and AC-14 green, and
  `npm run check` clean — including `noUncheckedIndexedAccess` and
  `exactOptionalPropertyTypes`.

**Phase 2: The due-Reminder sweep**
- **Goal:** the cron rings the phone on its own, exactly once per Reminder.
- **Scope:** fill `runScheduledJob`; the conditional claim on
  `sentAt IS NULL AND fireAt <= now`; dispatch through `sendPush` /
  `classifyPushOutcome` / `buildNotificationPayload`; release the claim on a
  retryable outcome; prune on `gone`; suppress and mark for `done` / `missed`
  Tasks. The payload's `route` may still be `/` at the end of this phase —
  phase 3 gives it somewhere better to point.
- **Success signal:** AC-5, AC-6, AC-7, AC-9 and AC-10 green; the local dev cron
  delivers a due Reminder to a real subscription once and only once.

**Phase 3: Per-Task route and Reminder UI**
- **Goal:** the owner can set a reminder without a terminal, and tapping one
  lands on the thing it is about.
- **Scope:** the new `AppRoute` variant and its codec; `sw.ts` and the SPA
  `postMessage` listener updated; the payload builder pointing at the Task; the
  pt-BR create/edit/delete surfaces for both shapes, using only tokens from
  `src/app/tokens.css` and the owned components under `src/app/components/ui/`.
  The **UI/UX review checklist** from
  `documentation/40-engineering/ui-ux-guidelines.md` runs on this phase and its

## Decisions Log

| Decision | Choice | Alternatives | Rationale |
|----------|--------|--------------|-----------|
| Sweep ordering | Claim before sending (conditional `UPDATE ... WHERE sent_at IS NULL`), releasing the claim only on a retryable push outcome | Send-then-mark (at-least-once); a lease column with expiry; a work-item table keyed on `(target, scheduled_for)` | The exit signal demands "none duplicated, none silent". Send-then-mark can duplicate; a plain claim can go silent. The release turns the common failure (a 429/5xx) into a retry, leaving only a hard crash — which `cron_runs` already records. A lease column would be a second mechanism for what `sent_at` already expresses |
| Meaning of a deadline for a relative reminder | End of the local day, 23:59 in `America/Sao_Paulo`, as one named constant in `src/shared/`, with the computed instant shown before saving | Refuse relative reminders on date-only Tasks (Todoist's answer); add a time-of-day column to Tasks; assume 09:00 | A Task carries no time, and refusing would make FR-025 unusable for most of the owner's Tasks. Showing the resulting instant keeps the arithmetic honest, and the single constant makes the open question a one-line change |
| Behavior when a Task's deadline moves | Recompute the relative Reminder's `fireAt` and say so on screen; never touch an already-sent row | Silently shift it (Apple Reminders); leave it frozen at the old instant; delete and ask the owner to re-create | Silent shifting is a documented community trap; a frozen reminder is a lie about a plan that changed. The honest-mirror principle already governs `missed` Tasks and applies here |
| Reminders for closed Tasks | Do not deliver; mark `sent_at` so the row is not reconsidered on every tick | Deliver anyway; delete the reminder on completion; leave unclaimed | A notification about something already finished is how an owner learns to ignore notifications. Marking rather than deleting keeps the record and keeps the sweep's scan cheap |
| Storage model | One absolute `fire_at` per Reminder, scanned directly by the existing `reminders_due_idx` | Expand a rule at sweep time; introduce ADR-0006's `next_fire_at` now | The table was designed for exactly this ("so no rule expansion ever happens on the hot path"). `next_fire_at` and its three recomputation points belong to units 9/17, and the roadmap already records the cost of inverting that order |
| Per-Task deep link | Treat it as new end-to-end work (route variant, codec, `sw.ts`, SPA listener), not merely as a device-proof of existing code | Prove the existing `/` path on-device and call the residual closed | `AppRoute` has no Task variant at all (`src/shared/app-route.ts:25`). The roadmap's residual understated the gap; scoping it as new work is what keeps phase 3 honest |
| Database change | None — reuse the existing `reminders` table | Add columns for a status enum or a delivery log | The existing columns cover every acceptance criterion, and adding a table would trigger the unit 5 export-completeness coupling for no gain |

## Research Summary

**Market Context**

The idempotency literature is unambiguous that exactly-once delivery is not
achievable across a network boundary; what production systems build is
at-least-once delivery plus idempotent processing
([oneuptime](https://oneuptime.com/blog/post/2026-01-30-exactly-once-delivery/view)).
The two orderings are explicitly opposed: sending first and marking second gives
at-least-once — never silent, possibly duplicated — while marking first gives
at-most-once
([traveling-coderman](https://traveling-coderman.net/code/node-architecture/idempotent-cron-job/)).
A Cloudflare Queues + D1 write-up demonstrates the claim-first shape with a
conditional `UPDATE` lease, deterministic ids derived from the target time rather
than the execution time, a unique index on `(target, scheduled_for)`, and
rescheduling from the original slot rather than from "now" when a tick runs late
([flaviocopes](https://flaviocopes.com/idempotent-scheduled-job-cloudflare-queues-d1/)).
Community work on schedulers treats catch-up for missed windows as an explicit
opt-in that logs at WARNING level rather than a silent default
([issue thread](https://github.com/NousResearch/hermes-agent/issues/27327)).

On the product side, Todoist requires a due *time* before it will accept a
relative reminder, because there is otherwise nothing to count back from
([Todoist](https://www.todoist.com/help/articles/introduction-to-reminders-9PezfU));
Apple Reminders stores the alert as an offset from the due date and therefore
shifts it silently when the due date is edited, a behavior its own community
documents as a trap with a "edit the due date first" workaround
([Apple discussions](https://discussions.apple.com/thread/4483492)); and Google
Tasks has no reminder engine of its own, borrowing Google Calendar's notification
settings, which weakens date-only tasks to all-day-event alerts
([TasksBoard](https://tasksboard.com/blog/google-tasks-reminders-guide)). Praesto
takes the opposite turn from Apple on the same question and answers the one
Todoist refuses.

Gaps the research did not close: no source confirmed whether these products
suppress reminders for already-completed items, no first-party Todoist
documentation covers what happens to a relative reminder when the due date is
edited, TickTick and Things were not examined within the query cap, and the
Cloudflare-specific idempotency prior art rests on a single blog post rather than
official documentation. AC-9's suppression rule is therefore a Praesto decision,
not an industry convention.

**Technical Context**

The `reminders` table exists in full with the columns this unit needs and the
`reminders_due_idx` on `(sent_at, fire_at)` described in its own doc comment as
"the cron's only scan" (`src/worker/db/schema.ts:233-264`); `ReminderDto` and
`toReminderDto` already exist and are consumed by the export route
(`src/worker/dto.ts:115-126`, `src/worker/routes/export.ts:35-52`), which is
today the only code path that reads the table. `runScheduledJob` is an empty
placeholder whose comment reserves it for this unit, wrapped by a
`runCronHeartbeat` that already times, catches and durably records every run
(`src/worker/cron.ts:5-51`). The full dispatch path — `sendPush`,
`classifyPushOutcome`, `buildNotificationPayload`, with prune-on-`gone` — is
proven and directly reusable (`src/worker/routes/push.ts:127-144`).
`src/worker/routes/tasks.ts:305-313` is the house route pattern: hand-rolled
validation, a `readJson` guard, `Object.hasOwn` partial updates, no zod.

Two genuine gaps. `AppRoute` is `"today" | "settings" | "notifications" |
"notifications-diagnostics"` with no Task variant
(`src/shared/app-route.ts:25`), so the notification deep link into a specific
screen is unbuilt rather than merely unproven. And `src/shared/dates.ts:22-37`
contains only `todayIn`; nothing converts a local calendar day plus an offset
into an epoch instant, and nothing computes `origin_offset_minutes` — that helper
is new. No `src/worker/routes/reminders.ts`, no reminder UI under `src/app/`, and
no reminder test file exist yet.
