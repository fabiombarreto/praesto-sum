## Source PRD

- `PRPs/prds/push-channel-proven.prd.md` — Implementation Phases row 3: "cron-heartbeat" — Goal:
  Make the cron's liveness a fact stored in the database rather than an inference from logs —
  Success signal: After a real cron tick in local dev, the diagnostics endpoint returns a `fresh`
  state with a run instant, and a deliberately throwing job body still produces a row.

## Summary

This phase stops `scheduled()` from being an empty stub. It adds a `cron_runs` table (migration
required — the first in this unit) and wraps the cron's future job body in a heartbeat that always
writes one row on completion, success or failure, inside a `finally` block, so a crash never leaves
the run unrecorded (AC-5). It adds a pure `src/shared` freshness classifier with three distinct
states — `fresh` (<10 min), `stale` (>=10 min), `unknown` (no run ever recorded) — never letting
`stale` stand in for `unknown` (AC-6). It teaches the existing `POST /api/push/test` route to
persist its own outcome as the "last dispatch attempt" (phase 2 computed these outcomes in memory
and threw them away; this phase is where they are stored). Finally it adds a bearer-gated
`GET /api/diagnostics` endpoint composing all four facts — last cron run, freshness, subscription
count, last dispatch attempt — into one response (AC-7). No Reminder is read; the due-Reminder scan
is unit 7's scope.

## User Story

As the owner, I want the cron's own liveness and the last push attempt's outcome recorded in the
database, so that a diagnostics screen (Phase 4) can tell me the channel is alive without me reading
`wrangler tail`.

## Problem Statement

`scheduled()` is a documented stub (`src/worker/index.ts:53-64`): nothing it does is observable.
Worse, the channel is silent when it breaks — a crashed cron run and a cron that never fired look
identical from the outside, because nothing writes anything down either way. Building unit 7
(Reminders) on top of an unobserved cron would make every future delivery bug undiagnosable, and
Phase 2's `POST /api/push/test` route already computes a rich per-endpoint outcome on every call and
discards it the moment the response is sent — there is no way to answer "what happened last time?"
without re-running it.

## Solution Statement

Two new D1 tables carry the two facts this phase must persist. `cron_runs` (migration required)
records one row per cron invocation: `startedAt`, `outcome` (`success`/`failure`, TypeScript union +
SQL CHECK per ADR-0006), `durationMs`, and `errorMessage` (populated only on failure). A new
`src/worker/cron.ts` module exports `runScheduledJob(env)` — an intentionally empty placeholder for
unit 7's due-Reminder scan, exported specifically so a test can override it to force a throw — and
`runCronHeartbeat(env)`, which times `runScheduledJob`, catches any throw, and writes exactly one
`cron_runs` row inside a `finally` block regardless of outcome. `scheduled()` in
`src/worker/index.ts` shrinks to a single call: `await runCronHeartbeat(env)`.

`push_dispatch_attempts` is a singleton table (mirroring `google_connections`'s CHECK-pinned single
row) holding the most recent `POST /api/push/test` outcome: `attemptedAt` plus `results`, a
JSON-encoded array of `{ endpoint, outcome }`. The route is updated to upsert this row on every call
using the same select-then-branch idiom the subscribe route already uses.

A pure `src/shared/cron-freshness.ts` module classifies a last-run instant against a reference
instant into exactly three states, mirroring `src/shared/push-outcome.ts`'s discriminated-union
shape: `fresh` when the gap is under 10 minutes, `stale` when 10 minutes or more, `unknown` when no
run was ever recorded (a `null` last-run instant) — the PRD explicitly forbids `stale` standing in
for `unknown`.

`GET /api/diagnostics` (new route, mounted under the existing `/api/*` `requireToken` gate) composes
all four: the last `cron_runs` row (mapped by a new `toCronRunDto`), the freshness classification,
`push_subscriptions`' row count, and the last `push_dispatch_attempts` row (its JSON `results`
parsed back into an array). A missing bearer token answers 401 with no body — free, from the
existing middleware — and a request with a valid token gets every field AC-7 names.

  `npm run db:migrate`); `npm run db:migrate:remote` and `npm run deploy` are never invoked by any

- **A retry/backoff scheduler for `retryable` push outcomes.** Out of this phase's scope, same as

- **Cron-run history pruning or a retention policy for `cron_runs`.** The PRD names no such
  requirement, and D1's free-tier storage ceiling is not remotely threatened by one row per 5
  minutes; a future phase may add one if it ever is.

### Task 3: CREATE `src/shared/cron-freshness.ts`

**ACTION**: Create a module exporting `export type CronFreshness = "fresh" | "stale" | "unknown";`
and `export function classifyCronFreshness(lastRunAt: Date | null, now: Date): CronFreshness`. When
`lastRunAt` is `null`, return `"unknown"` — no run was ever recorded, and this must never collapse
into `"stale"` (PRD AC-6's explicit warning). Otherwise compute `now.getTime() - lastRunAt.getTime()`
in milliseconds; a value under `10 * 60 * 1000` (10 minutes, exported as a named constant
`FRESHNESS_THRESHOLD_MS`) returns `"fresh"`; `10 * 60 * 1000` or more returns `"stale"`. The
threshold is a closed boundary on the stale side (`>=`), matching AC-6's own wording ("a gap of 10
minutes or more is `stale`").

### Task 4: CREATE `src/worker/cron.ts`

**ACTION**: Create a module exporting two functions.

1. `export async function runScheduledJob(_env: Env): Promise<void> {}` — an intentionally empty
   placeholder. Document in a comment that this is where unit 7's due-Reminder scan will land, that

2. `export async function runCronHeartbeat(env: Env): Promise<void>` — records `const startedAt =
   new Date()` and `const startMs = Date.now()` before calling `runScheduledJob(env)` inside a
   `try`. On success leave `outcome: "success"` and `errorMessage: null` (both declared with `let`
   before the `try`). On a caught error, set `outcome = "failure"` and `errorMessage =
   err instanceof Error ? err.message : String(err)`. In a `finally` block — so it runs whether the
   `try` succeeded or threw — compute `durationMs = Date.now() - startMs` and insert exactly one row
   into `cronRuns` via `createDb(env).insert(cronRuns).values({ id: crypto.randomUUID(), startedAt,
   outcome, durationMs, errorMessage })`. This is what makes AC-5 hold: the row is written
   unconditionally in `finally`, so a throw inside `runScheduledJob` still leaves a durable record
   rather than an absent one.

## Acceptance Criteria

- **AC-A1 (PRD AC-5):** Given the cron fires, when `scheduled()` completes, then a row exists in
  `cron_runs` carrying the start instant, the outcome `success`, and the duration; given
  `runScheduledJob` throws, then a row still exists carrying outcome `failure` and the thrown

- **AC-A2 (PRD AC-6):** Given a last-run instant and a reference instant, when
  `classifyCronFreshness` runs, then a gap under 10 minutes returns `fresh`, a gap of 10 minutes or
  more returns `stale`, and a `null` last-run instant (no run ever recorded) returns `unknown` —
  three distinct states, `stale` never standing in for `unknown`.
- **AC-A3 (PRD AC-7):** Given a request to `GET /api/diagnostics` without a valid bearer token, then

  `POST /api/push/test` dispatch attempt's instant and per-endpoint outcomes (or `null` when no
  dispatch has ever been attempted).
