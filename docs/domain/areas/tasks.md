# Tasks

**Primary responsibility:** everything the owner intends to do — capture, organize, complete. The MVP (Phase 1) scope.

**Entities:** Task (see `docs/domain/glossary.md`); relates to Life Area, Event (N:N), Reminder.

## Business rules (owner-validated 2026-08-03)

- A Task has a completion lifecycle `open → done`, and completion is undoable (FR-003).
- A Task may carry a **deadline** (complete *by* a date) OR a **scheduled date** (do *on* a date) — distinct semantics, never conflated (FR-005).
- Tasks never convert into Events; a Task may be linked to any number of Events and vice versa, navigable from both sides (FR-010, Phase 2).
- A Task with **no date** can recur too (ADR-0014, 2026-10-08): the series has `dateMode: "none"`, its occurrences carry no deadline or scheduled date but keep `occurrence_date`, and the sweep and successor behave as for dated ones; the successor is spawned when the predecessor closes but is listed only from its own `occurrence_date` (a dateless daily Task completed today reappears tomorrow).
- Tasks can recur (FR-009, Phase 1) per ADR-0006: a **Recurrence Series** holds the shared rule + template; each occurrence is a real Task row; **at most one open occurrence per active series** (unique index); completing spawns the next (calendar- or completion-anchored per series). Delivered end to end by unit 9 `recurring-tasks`: the pure expansion function (`src/shared/recurrence.ts`), `POST/GET/PATCH /api/series`, successor spawning on completion, and the *Repetir* control in the Task sheet (with a series glyph on the row) that lets the owner register a series without leaving the screen he already uses.
- An occurrence superseded without completion becomes **`missed`** (terminal, system-written) — every skipped cycle leaves a permanent record. The daily cron's missed sweep (`src/worker/cron.ts`, before the Reminder sweep) writes it when the series' local day reaches the next occurrence's date; each whole cycle that passed leaves its own row. The screen lists a `missed` Task under *Não concluídas* (collapsed by default, on *Hoje* and in search) and never under *Concluídas*, which holds `done` Tasks only. Done + missed rows are the realization history powering adherence visibility (FR-011) and repeated-miss notifications (FR-012) — the honest-mirror principle (vision principle 6). The read side exists as `GET /api/series/adherence` (adherence-mirror phase 2): per series, `done`/`closed` counts, the current streak and the recent misses are computed from those rows in the series' own time zone, never from the stored counters. The per-series record is surfaced by the *Aderência* route (`/settings/adherence`: *N de M feitas*, the current streak and the dates of recent misses, never a percentage) and by one plain-text line on *Hoje* below the chip row, shown only when an active series has at least two misses in the 30-day window (adherence-mirror phase 3).
- A Task can be edited after capture (FR-002, shipped in unit 2): `PATCH /api/tasks/:id` covers title, description, the two dates and priority. An omitted key leaves the field unchanged; an explicit `null` clears it. Setting one date clears the other, and editing a recurrence occurrence sets `detached` (ADR-0006). Since 2026-09-30 `detached` is on the wire (`TaskDto.detached`, AC-30), so the sheet tells the owner when an occurrence no longer follows its series — before that the flag was set silently.
- **Repeated-miss nudge state (FR-012, repeated-miss-nudge phase 2).** A series carries two columns beyond its rule: `nudge_muted` (owner preference, default false; edited with `PATCH /api/series/:id { nudgeMuted }`, per series, leaves Reminders alone) and `nudged_at` (system claim marker, null until a nudge is sent; cleared when an occurrence is completed, never by a `missed` close; not exposed on the series wire, present in the export). Migration `0006` adds both additively. The decision itself is the pure `src/shared/nudge.ts`; the cron step that sends the nudge and sets the marker has shipped (phase 3, below); the screen for the mute has shipped (phase 4, below).
- **Repeated-miss nudge cron step (FR-012, repeated-miss-nudge phase 3).** `sweepRepeatedMissNudges` (`src/worker/cron.ts`) runs in `runScheduledJob` after the missed sweep (a just-recorded third miss counts) and after the Reminder loop (a nudge can never delay a due Reminder). For each active task series whose trailing run reached 3 consecutive `missed` occurrences, at local time >= 09:00 in the series' zone, not muted and not yet nudged (`decideNudge`), it claims the run with a conditional `UPDATE recurrence_series SET nudged_at = now WHERE id = ? AND nudged_at IS NULL` and sends ONE push to every stored subscription: title = the series title cut to 30 characters (fallback *Tarefa recorrente*), pt-BR body, tag `nudge-<seriesId>`, deep link `/tasks/<open occurrence id>` (`src/shared/nudge-copy.ts`). A `gone` outcome (404/410) prunes that subscription; a `retryable` outcome releases the claim (`nudged_at` back to null) so the next run retries. No stored subscription, or no open occurrence, takes no claim at all. A MUTED series reaching the threshold has its run consumed (`nudged_at` set, nothing sent), so unmuting does not fire an old run. Each series is isolated: a failure releases that series' claim, the loop continues, and one error is thrown at the end; `runScheduledJob` defers it (like the missed sweep's) so `cron_runs` records the run as failed without blocking Reminders. Open edge: when every stored subscription is pruned as `gone` in the same run, the claim stays set (parity with the Reminder sweep), so that run is not retried. The closed-row loading and open-occurrence lookup shared with the series routes live in `src/worker/series-closed-rows.ts`. 
- **Repeated-miss nudge mute UI (FR-012, repeated-miss-nudge phase 4).** In the series section of the Task sheet, an occurrence of an ACTIVE series shows a switch labelled *Avisar após 3 não concluídas seguidas* (checked = `!nudgeMuted`; status text *Avisos ativos para esta série.* / *Avisos silenciados. Seus lembretes continuam normais.*). It is absent for a one-off Task and for an ended series. The switch persists IMMEDIATELY through `PATCH /api/series/:id { nudgeMuted }` — a deliberate exception to "nothing is saved without *Salvar*", because it is a per-series preference, not an edit of the Task being composed. The Aderência route row shows *Avisos silenciados* for a muted series (`SeriesAdherenceDto.nudgeMuted`, `formatNudgeMuted` in `src/shared/adherence-view.ts`). Pure helpers: `src/shared/nudge-switch.ts`; state lives in `useSeriesSheet`. Device proof (AC-17: the nudge observed on the owner's device) is still owed.
- **A series' rule is editable, and the change applies from the next spawn** (PRD D11, amended 2026-09-29 — option (a)). `PATCH /api/series/:id` accepts `freq`, `interval`, `byWeekday`, `byMonthday`, `anchorMode` and the end condition; the open occurrence keeps its date; **`dtstart` stays frozen and is refused**, because it is the series' origin and the alignment every period is computed from. After a rule edit the successor is the **next date** the new rule produces after the completed occurrence — even inside the same cycle (owner's decision, 2026-09-30); whether that cycle was already met is the owner's call, made by deleting the extra occurrence, which skips it.
- On a series occurrence's sheet, title, description and priority follow **"Aplicar a"**: *Toda a série* (default) edits the template, which reaches the open occurrence without detaching it; *Só esta ocorrência* edits the occurrence alone and detaches it. A date change is always an edit to that occurrence. The split is `planSeriesOccurrenceSave` in `src/shared/series-edit.ts`, pure and tested. Ending a series is irreversible and asks once.
- Tasks are listable and filterable by completion status, dates and priority (FR-007). Priority is optional (FR-006, unit 2 `task-detail-and-dates`): exactly three values, `high | normal | low`, enforced by a TypeScript union AND the `tasks_priority_chk` CHECK. `NULL` means "not set" and sorts as `normal`. As of unit 3 `today-view-and-filters` phase 1 (2026-08-23), the FR-007 filters are enforced in SQL by the list route's `WHERE` clause beside the frozen urgency ordering (`src/worker/routes/tasks.ts`): `from`/`to` compare against `coalesce(deadline, scheduledDate)`, so a Task with neither date falls outside every range, and `priority=normal` also matches the `NULL` case above. As of unit 8 `text-search` phase 1 (2026-09-15, FR-040), the same route accepts an optional `q` parameter: every whitespace-separated word of `q` must occur, in any order and anywhere, in the Task's title or description, case- and diacritic-insensitive, across every status (`open`/`done`/`missed` alike, with no `status` filter needed), and composes with the other filters. A blank/whitespace-only `q` or one over 100 characters is rejected with `400` naming `q`. The search route (UI) — reached from the header's *Pesquisar* icon, results grouped like *Hoje* — is built in unit 8 phase 2; the owner's device verification (AC-12) and the UI/UX checklist recording remain owed before the unit can close.
- A Task may belong to a Life Area (FR-008, unscheduled).
- Capture must be near-zero friction on any device (FR-045 — vision principle 5).

## Phase 1 FR set

FR-001..005, FR-007, FR-009, FR-011, FR-012 + cross-cutting FR-040/041/042/044/045. Exit criterion: the owner manages daily Tasks in the assistant instead of scattered notes.

## Relationships

- **Reminders** may point to a Task (deadline nudges).
- **Events** relate via N:N links (Phase 2).
- **Life Areas** group Tasks.

## Resolved 2026-08-03

- Lifecycle is `open → done` only in the MVP; deletion covers abandonment.
- A dated Task (deadline or scheduled) DOES appear on calendar views, visually distinct from Events.
- Life Area is optional; area-less Tasks surface in an implicit "Unsorted" grouping (no stored default).
