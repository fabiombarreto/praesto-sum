# Architecture

> Derived from `documentation/30-architecture/` and ADR-0003..0005 (`documentation/60-decisions/`) — those files are authoritative. Update both together.

## Stack

- **Runtime/hosting:** Cloudflare Workers, free plan — one Worker serves everything: static assets (SPA), `/api/*`, and the `scheduled()` cron handler (ADR-0003).
- **Database:** Cloudflare D1 (SQLite-class, managed) — the single canonical copy of all data. Access via Drizzle ORM (`drizzle-orm/d1`).
- **Frontend:** React 19 single-page application, TypeScript strict, bundled by Vite with `@cloudflare/vite-plugin`; PWA via `vite-plugin-pwa` in `injectManifest` mode with a hand-owned `src/sw.ts` (ADR-0004/0005).
- **API:** Hono 4 in the Worker — bearer-token middleware on every route (single user, no accounts).
- **Notifications:** Web Push (`web-push` library under `nodejs_compat`), fired by the Workers cron trigger.

## Architectural pattern

Thin client over a canonical server store: the PWA holds no authoritative state and there is **deliberately no merge, sync, or offline-write logic anywhere** (ADR-0003). SPA without SSR/RSC is a recorded final position, not deferred debt (ADR-0005).

## Repository layout (real since the 2026-08-03 scaffold)

| Path | Contents |
|---|---|
| `src/app/` | React SPA: `App.tsx`, `api.ts` (typed client; token accessors `readToken`/`saveToken`/`clearToken` delegate to `src/shared/token-store.ts`), `token-storage.ts` (IndexedDB + `localStorage` adapter and `requestPersistentStorage()` — the exempt glue under `docs/context/methodology.md`'s "Browser-API work" rule), `pwa.ts`, `main.tsx` |
| `src/sw.ts` | Service worker: precache, push, notificationclick |
| `src/shared/` | Environment-agnostic: `api.ts` wire contract + pure domain logic |
| `src/worker/` | `index.ts` (fetch + scheduled), `auth.ts`, `dto.ts`, `routes/`, `push/`, `db/` |
| `migrations/` | Numbered SQL generated by drizzle-kit, applied by wrangler |
| `test/` | Vitest suites running inside workerd against an ephemeral D1 |
| `public/` | PWA manifest, icons |
| `documentation/` | Authoritative project docs (vision, requirements, ADRs) |
| `docs/` | This relay context system (derived) |

Per-target tsconfigs with project references make an app/worker boundary violation a compile error. `src/shared/` compiles into every target, so it carries no DOM/Worker globals and no runtime dependencies.

## Current implementation state (Phase 1)

Shipped: Phase 1 schema (`life_areas`, `recurrence_series`, `tasks`, `reminders`, `push_subscriptions`) with the ADR-0006 invariant indexes; token-gated API; Task create / list / complete / reopen / delete; walking-skeleton PWA.

**In production since 2026-08-04** at `https://praesto.fabiobarreto.workers.dev` (chores C1–C3): real D1 `praesto-db` migrated, `API_BEARER_TOKEN` stored as a Worker secret, PWA icons generated by `scripts/generate-icons.js`, cron registered at `*/5 * * * *`. Deploy steps and smoke test: `documentation/40-engineering/dev-environment.md#deploy-runbook`.

Not built yet: recurrence machinery (the `scheduled()` handler is an empty stub), Web Push dispatch, export (FR-042), search (FR-040), Life Area and Reminder endpoints. Events and their exceptions are Phase 2 and absent from the schema by design.

## Data safeguards (binding, ADR-0003)

- Day-1 export of 100% of the data as JSON + iCalendar (FR-042).
- Automated export snapshots shipped to the owner's PC — Cloudflare never holds the only copy (FR-043).
- No offline write queue without a superseding ADR.
- Every API route requires the auth token; only the PWA shell is unauthenticated.

## External services

- **Cloudflare** (Workers, D1, cron) — platform; can technically read D1 (consent recorded in ADR-0003).
- **Web Push service endpoints** (browser vendors) — deliver notifications.
- **Google Calendar** — decided by ADR-0007 (bidirectional, Events only) and **access proven** by chore C11 on 2026-08-11, but **no integration code exists yet** — unit 4 `google-calendar-read` writes it. The OAuth app `praesto-sum` is published *In production* with both sensitive Calendar scopes and **no** verification submission; a working refresh token is stored as the Worker secret `GOOGLE_REFRESH_TOKEN`. Two measured facts unit 4 must design around: `calendarList.list` answers **403 insufficient scopes** under `calendar.events.readonly` (so FR-027's calendar picker needs a scope decision), and the owner's entire calendar history is 401 events in **one** page at 4.45 ms CPU, well inside the free-plan ceiling. Details in `documentation/30-architecture/architecture-overview.md`.
