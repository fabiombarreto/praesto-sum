## Candidate Decisions (for operator review)

The following were observed in the diff but are implementation choices, inferred patterns or generalisations, so they were NOT written to `docs/decisions.md` or `docs/anti-patterns.md` per the PRESERVE-ENTIRELY rule. The operator should review them and add them manually if they are stable:

- **An optional, never-seeded draft field for a sheet control whose unchosen state must never be sent.** `TaskDraft.lifeAreaId` is absent until the owner touches the group, and `draftFromTask` deliberately does not seed it, so a kept draft cannot re-send an id that changed or vanished on the server and an unchosen area cannot detach an occurrence (ADR-0006). It is stated in the code comments but as an implementation rationale, not a project-wide rule. If the owner wants it recorded, the natural form is an anti-pattern ("seeding a draft with a value whose re-send detaches or overwrites") or a convention for any future sheet control that writes to a detach-on-edit entity.
- **Owner-sized chip groups wrap; fixed groups scroll.** `ChipGroup`'s opt-in `wrap` is the first group laid out on several rows because its length is the owner's own (up to 12 areas plus *Sem área*). Phase 4's filter sheet will reuse it. This belongs in `documentation/40-engineering/ui-layout-standard.md` or the guidelines if promoted, which is outside this agent's scope and is where phase 4's AC-25 sync already looks.
- **A secondary read that enriches a screen is its own atom and degrades to absence.** `useLifeAreas` and the adherence line on *Hoje* now share the shape: the data is held apart from the Task list, a failure leaves `null`, nothing is announced, and the list never waits for it. Two instances make it look like a convention; it is not written in `docs/context/conventions.md` because two cases are an observation, not a stated rule.
