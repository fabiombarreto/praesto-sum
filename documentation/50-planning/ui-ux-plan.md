# UI/UX Plan

> **Purpose:** The plan that gives Praesto its visual and interaction foundation — UI/UX guidelines, a layout standard, a visual identity, one UI library and a design pass over the existing screens — deliberately kept apart from the [roadmap](roadmap.md), whose delivery units are on hold until this plan closes.
> **Update when:** An activity changes state, an open question below is answered, a decision lands as an ADR, or the hold lifts. Status flips `draft → active` when the owner has answered the open questions in [Decisions to make](#decisions-to-make); it flips `deprecated` when the exit criterion is met and the roadmap resumes (its outputs live on in `10-product/` and `40-engineering/`).

## The brief (owner, 2026-08-18)

The screens are bare: no guide, no pattern, no life. That stops now, before unit 3. In the owner's words, restated:

1. **Research** UI/UX best practices for PWAs and write a **UI/UX guidelines** document, referenced from `CLAUDE.md` and followed whenever the interface changes.
2. **Research layout ideas** and fix a **layout standard** to follow.
3. Keep the interface **simple, minimalist, few elements per screen** — but with a **younger ambience, inspired by the gamer community** (Steam, Discord, Epic). Not over-complicated; **beautiful, fun, modern**.
4. Adopt **one UI library** as the standard and follow its components as far as possible — **well consolidated, constantly updated, large community**.
5. *(added later the same day)* **Define a visual identity** for the application, following the **step-by-step a designer uses** to define the identity of a digital product.

The owner asked to be questioned on anything that does not fit the project and to receive suggestions on what the brief left out. Both are below.

## Scope

**In:** the five deliverables above; the mark (keep, evolve or replace the current plumb-bob — decided inside the identity work, not assumed); applying everything to the screens that already exist (token gate, capture + list, task detail, PWA chrome: icons, splash, manifest colours, install/update prompt, loading/empty/error states); a design workflow every later unit follows; the ADRs the choices produce.

**Out (unless an open question below says otherwise):** new features — unit 3+ functionality stays in the roadmap; gamification *mechanics* (XP, levels, badges); marketing artefacts (there is no audience but the owner — no landing page, no brand campaign, no merchandise); a browser/e2e test tier (its trigger stays at unit 6, per the [testing strategy](../40-engineering/testing-strategy.md)); Figma-driven pipelines (`figma_track` stays `false` unless the owner opts in).

**Not held by this plan:** chores (C12 on 2026-08-19), backlog triage, and production hot-fixes.

## What the product principles demand of the design

The [vision](../10-product/vision.md) already constrains the look more than the brief says. Every activity below is checked against these:

| Principle | Design consequence |
|---|---|
| 1 Simplicity over completeness | Few elements per screen is a *rule*, not a taste. Every visible element must earn its place; density is the enemy, and Steam-style density is exactly what we do **not** borrow. |
| 5 Effortless in, effortless out | Capture is the hero of the home screen — one thumb, one field, one tap; retrieval (search, unit 8) gets a permanent, obvious entry point in the layout standard even before it ships. |
| 6 Honest mirror | "Fun" never hides misses. Celebration on completion is fine; softening, hiding or gamifying a `missed` away is not. Adherence data (unit 11) must be visually first-class, not a buried stats page. |
| 3 Sustainable for one person | One library, one token set, one styling pipeline. No bespoke CSS zoo, no second component source, no design system the owner cannot maintain in an hour a day. |
| 4 Adapts to the owner | The owner's own references (screenshots he likes) are the design brief; nothing is imposed "because Discord does it". |
| ADR-0004 / CON-007 | Android phone first, Windows desktop second, no iOS. Standalone display, safe areas, touch targets and Web Push permission UX are Android-Chrome facts, not iOS folklore. |

### How A2 runs — the visual-identity step-by-step

The professional arc is the same in every studio surveyed (Wheeler's five phases; Focus Lab, Ramotion, Koto; Linear's and Discord's own write-ups): **research → strategy → visual exploration → identity system → guidelines → validation in use**. Wheeler says solo practitioners run the same phases, "not as deep and broad" — so this is that arc at owner scale, in hours. Steps 2.1 and 2.2 are the owner's own work and cannot be delegated; everything else is prepared for him and decided by him.

| Step | Purpose | Method | Deliverable | ~h |
|---|---|---|---|---|
| 2.1 Audit + reference landscape | Know what exists and what the owner actually likes before choosing anything | Inventory the current mark, manifest colours and every screen state (screenshots). The owner collects **6–8 screenshots of apps he admires** (Discord, Steam, Epic, plus whatever else he uses and likes); place them on a two-axis map (dense ↔ sparse, playful ↔ serious); write a borrow / avoid list per reference | `PRPs/reports/visual-identity/01-audit-and-landscape.md` with images | 1 |
| 2.2 Attributes & personality | Turn "younger, gamer, simple, honest" into a few agreed words every later choice is judged against | Card sort of ~40 adjectives into **is / would like to be / is not**, at most 3 per column (Bloomstein); 6–8 semantic-differential sliders (playful ↔ serious, dense ↔ sparse, loud ↔ calm, warm ↔ cool, hand-made ↔ engineered, gamer ↔ corporate…) marked *today* vs *target* | Attribute sheet: 3 IS, 3 IS-NOT, slider targets | 1 |
| 2.3 One-page brief | Fix the strategy in writing so the visuals have a target and the ADR a rationale | Name + meaning + pronunciation (*praestō*: classical [ˈprae̯s.toː], ecclesiastical [ˈprɛs.to] — "at hand, at your service"); user and context (phone-first, sunlight and night, one thumb); the attributes; Neumeier's who / what / why-it-matters; the product-principle consequences above; two references and what to borrow / reject | Brief section of the identity doc | 0.5–1 |

| 2.5 Moodboard | Make the attributes visible before drawing anything — the cheapest place to say no | 12–20 items (screens, type specimens, colour pairs, one motion clip, icon styles) on one HTML page viewable on the phone; each tagged with the attribute it serves; anything matching an IS-NOT word is deleted | `PRPs/reports/visual-identity/moodboard.html` | 1 |

## Suggestions the brief did not cover

- **Design tokens as the contract, the library as the implementation.** Colours, type, radius, spacing and motion live in one token file (CSS variables) owned by us; the library consumes them. That is what keeps a library swap or a light theme from becoming a rewrite, and what lets `docs/` describe the look in one place.
- **Self-host fonts and icons.** No external font or icon requests: they break offline (the precache glob already includes `woff2`), leak the owner's usage to a third party (CON-005 spirit) and add first-paint latency on the phone. One variable font file + one icon set, both open-licensed, both precached.
- **A UI review checklist inside the guidelines**, short enough to run on every PR: contrast, targets, states (loading/empty/error/offline), copy voice, safe areas, reduced motion, phone-first. Reviewers — human or agent — check boxes, not vibes.
- **State design before screen design.** Loading, empty, error, offline, "server unreachable" (ADR-0004 makes this mandatory on every screen), "new version available" and notification-permission priming are where bare apps look bare. A3 designs them once as patterns.
- **A `/design` playground route in dev only** — one page rendering every token and component state, so a change is checked in one place on the phone. Excluded from the production bundle.
- **Performance budget written down:** first load on the phone under a defined JS/CSS size and LCP target, checked at A5 with the built bundle, so "beautiful" does not silently cost the quick-capture second.
- **Screenshots as records.** Every design decision that the owner takes "looking at it" is recorded with the screenshot filed under `PRPs/reports/` (`visual-identity/` for A2, `ui-design-pass/` for A5) — the same lesson unit 2's history taught about unverifiable claims.
